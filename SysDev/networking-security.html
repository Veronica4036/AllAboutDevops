Q1 · HTTP Status Codes   🟢 HIGH


Problem:   Name HTTP code categories and explain them. Give specific examples.

REFERENCE 
1xx  Informational    100 Continue, 101 Switching Protocols
2xx  Success          200 OK, 201 Created, 204 No Content
3xx  Redirection      301 Moved Permanently, 302 Found, 304 Not Modified
4xx  Client Error     400 Bad Request, 401 Unauthorized, 403 Forbidden,
                      404 Not Found, 429 Too Many Requests
5xx  Server Error     500 Internal, 502 Bad Gateway, 503 Unavailable,
                      504 Gateway Timeout

# Common gotchas
401 vs 403   401 = not authenticated; 403 = authenticated but not allowed
301 vs 302   301 permanent (cache); 302 temporary (do not cache)
502 vs 504   502 upstream returned bad response; 504 upstream timed out
429          Rate limited; check Retry-After header

🔍 DEEP DIVE — THE FIRST DIGIT IS THE WHOLE STORY

Every HTTP status code is three digits, but the first digit alone tells you who's to blame and what action to take. Once you internalize that, the rest is detail.

1xx — Informational (rare, usually invisible). The server is still processing; more data is coming. 100 Continue is the protocol-level "send me the body, I've verified the headers" response when a client uses Expect: 100-continue. 101 Switching Protocols is what the server sends when you upgrade from HTTP to WebSocket. You almost never see these at the application layer — they're handled by the stack below.

2xx — Success.
  • 200 OK: the default "it worked"; response has a body.
  • 201 Created: after POST; the Location header should point at the new resource. This is a signal of API quality.
  • 202 Accepted: "I got your request, I'll do it asynchronously." Used for long-running operations; pair with a Location header pointing to a status endpoint.
  • 204 No Content: success but nothing to return — typical for DELETE, or PUT when the resource didn't change in ways the client cares about. Must have no body.
3xx — Redirection & Caching.
  • 301 Moved Permanently: browsers and search engines cache this forever. Use it for permanent URL changes. Getting this wrong (serving 301 during a test migration) is how you end up with users stuck redirecting to a dead path for weeks.
  • 302 Found / 307 Temporary Redirect: "go here for now, but ask me next time." 307 preserves the method (POST stays POST); 302's semantics historically flipped that, which is why 307 exists.
  • 304 Not Modified: the resource hasn't changed since the client's cached version — sent in response to conditional requests with If-None-Match (ETag) or If-Modified-Since. The response has no body — it saves bandwidth.
4xx — Client did something wrong. Don't retry without fixing the request.
  • 400 Bad Request: malformed — missing field, wrong type, broken JSON.
  • 401 Unauthorized vs 403 Forbidden: the most common mix-up. 401 = "I don't know who you are" (credentials missing or invalid — send them and retry). 403 = "I know who you are and you still can't have this" (retrying with same creds won't help). The naming is historical and misleading; remember it by "401 needs login, 403 needs different permissions".
  • 404 Not Found: resource doesn't exist. Sometimes used to hide 403 to avoid leaking existence — not bad practice for private resources.
  • 405 Method Not Allowed: the URL exists but your verb doesn't apply (e.g., PUT /search). The response must include an Allow header listing the valid methods.
  • 409 Conflict: you tried to modify something that's in a state that makes your edit invalid — typical for optimistic concurrency control ("your version is stale").
  • 422 Unprocessable Entity: syntactically valid JSON, but the values fail validation ("email field not a valid email"). Some APIs prefer 400 for this — pick one and be consistent.
  • 429 Too Many Requests: rate limit hit. Must include Retry-After (either seconds or an HTTP-date). This is the feedback loop that lets a well-behaved client back off — honoring it is the core of the Retry + Backoff pattern.
5xx — Server (or something between you and the server) broke. Retrying may help.
  • 500 Internal Server Error: uncaught exception, bug. Generic failure; the server is telling you "something went wrong on my side and I won't be more specific". Don't retry idempotent-only requests blindly — a 500 on a POST /charge could mean "the request succeeded but the response was lost".
  • 502 Bad Gateway: a proxy or load balancer got a response from the upstream but it was garbage — protocol violation, wrong bytes. Typically means "upstream crashed or restarted mid-request".
  • 503 Service Unavailable: the server is up but can't serve right now — overload, maintenance, draining. Retry-After is the right header to include. 503 is what you'd serve during a deployment.
  • 504 Gateway Timeout: the upstream didn't respond in time. 502 vs 504 vs 503: 502 = upstream talked but said gibberish; 504 = upstream didn't talk; 503 = this server chose not to. Distinguishing these lets you know which layer to look at first.
What makes this an L4 question: the interviewer wants to see you think about idempotency + retries + blast radius. A GET returning 500 is safe to retry; a POST returning 500 may have succeeded server-side before the failure. 429 and 503 retries need backoff. 4xx except 429 should not be retried without human review. That understanding is what separates "someone who memorized the codes" from "someone who's debugged production".

The "what codes does your API actually emit?" move: curl -sI -o /dev/null -w "%{http_code}\n" $URL gets just the status code. For production systems, the useful question is "what's our 5xx rate over the last 1h?" — alert on any sustained 5xx above ~0.1%. CloudWatch, Datadog, Prometheus all expose HTTP status as a metric for this.

Q2 · TCP vs UDP   🟢 HIGH


Problem:   Explain the differences between TCP and UDP. When would you use each?

COMPARISON 
TCP  Connection-oriented, reliable (retransmission), ordered,
     flow control, congestion control. Higher overhead.
     Use for: HTTP, SSH, FTP, email.

UDP  Connectionless, no delivery guarantee, no ordering,
     lower overhead. Use for: DNS, streaming, gaming, VoIP,
     real-time metrics.

# Trade-off: reliability vs latency/overhead

# When app-level reliability is preferred over TCP:
# - Real-time where stale data is worse than lost
# - Multicast/broadcast (UDP only)
# - QUIC/HTTP3 built on UDP for 0-RTT and no head-of-line blocking

🔍 DEEP DIVE — WHY BOTH EXIST

The real question is "why did the IP stack design two transport protocols?" Every other decision flows from that.

IP (the layer below) is unreliable by design. Packets can be dropped, reordered, duplicated, or corrupted. TCP and UDP are the two honest answers to "what do you want the transport layer to do about that?". TCP says "hide all of it from the application — guarantee a byte stream arrives in order". UDP says "don't try, just hand each packet over as-is and let the application decide".

TCP gives you four guarantees, and each one costs:
  • Delivery — via sequence numbers, ACKs, and retransmission on timeout. Cost: an extra round-trip of handshaking and holdbacks on packet loss.
  • Order — receiver buffers out-of-order segments until the missing one arrives. Cost: head-of-line blocking — a single lost packet stalls the whole stream until it's retransmitted. This is why loading many small resources over HTTP/1.1 on a lossy link feels worse than their size would suggest.
  • Flow control — receive window (advertised in TCP headers) lets a slow receiver say "don't send more than N bytes until I ACK". Prevents the sender from overwhelming the receiver's buffer.
  • Congestion control — congestion window, managed by the sender, grows on success (AIMD, CUBIC, BBR) and shrinks on loss. Keeps the network itself from collapsing under load. This is why a cold TCP connection starts slow and ramps up (TCP slow start).
UDP gives you almost nothing — and that's the point. No handshake, no sequencing, no retransmission, no flow control. Each packet is independent. For applications where losing a packet is fine (video frames: a missing frame is a glitch, not corruption; DNS: just retry the query; gaming: new position supersedes old), UDP's lower overhead is a feature. You save one RTT of handshake + any retransmission delay.

The interesting modern case: QUIC / HTTP/3. Google and others rebuilt reliable transport on top of UDP. Why? Because head-of-line blocking in TCP is a kernel-level problem — you can't fix it without OS changes, which ship slowly. QUIC runs in userspace, uses UDP for packets, and does its own flow/congestion/reliability per-stream, so one lost packet in stream A doesn't block stream B. It also merges the TCP and TLS handshakes into one, saving an RTT on every new connection. Same four guarantees, better implementation, because UDP didn't lock them out of the protocol evolution loop.

The "DNS uses UDP" nuance: DNS uses UDP by default for speed (a query and response fit in one packet each, no handshake), but falls back to TCP when the response is too large to fit in a single UDP packet (originally 512 bytes, now often 4096 with EDNS). That's why port 53 is open on both UDP and TCP on any DNS server. DNSSEC responses and zone transfers (AXFR) require TCP.

When you'd actually choose UDP and build reliability yourself: real-time streaming, VPNs (WireGuard, OpenVPN), game servers, video calls (WebRTC), service-to-service messaging in a trusted network where latency matters more than absolute delivery. If you can tolerate occasional loss or you have your own retry logic, the overhead of TCP's guarantees is wasted work.

Interview escalation: if the interviewer digs, they're probing for Nagle's algorithm (TCP coalesces small writes to avoid packet spam; disabled with TCP_NODELAY for low-latency apps), SO_REUSEADDR / SO_REUSEPORT (port binding after abrupt close), TCP keepalive (detect dead peers without application-level pings), and how TCP handles network partitions (connections can be half-open if one side rebooted silently — keepalive or app-level heartbeats are the fix).

Q3 · DNS Record Types   🟢 HIGH


Problem:   What types of DNS records do you know? Explain what each is used for.

REFERENCE 
A      hostname -> IPv4 address
AAAA   hostname -> IPv6 address
CNAME  alias -> another hostname
MX     mail exchange servers (priority + host)
NS     authoritative nameservers for the zone
SOA    zone authority / serial / refresh / retry / expire / TTL
TXT    arbitrary text; SPF / DKIM / DMARC / domain verification
PTR    reverse DNS (IP -> hostname)
SRV    service location (service.proto.name -> port + host)
CAA    which CAs may issue certificates

🔍 DEEP DIVE — DNS IS A DISTRIBUTED KEY-VALUE STORE WITH TYPED VALUES

Every DNS record is a tuple (name, type, TTL, value). The name is the key you look up (www.example.com); the type determines how the value is interpreted. Different types exist because "name → string" isn't enough — you need "name → IPv4 address", "name → mail server with priority", "name → authoritative signature for my domain". DNS grew by adding more types, not by changing the schema.

A and AAAA — the workhorses. A maps a name to a 32-bit IPv4 address; AAAA ("quad-A") maps to a 128-bit IPv6. Why the weird name? A single A record holds 4 bytes, and AAAA holds 4× that. When a client calls getaddrinfo("foo.com"), the resolver typically queries both in parallel (dual-stack), and the client prefers IPv6 if present — behaviour called Happy Eyeballs. Multiple A records on the same name produce DNS round-robin — the resolver rotates which IP it returns first, a poor-man's load balancer.

CNAME — alias to another name. "www.example.com is really example.com". Resolvers chase the chain until they hit an A/AAAA. Two important rules: (1) a CNAME can't coexist with other records at the same name — if www.example.com is a CNAME, it can't also have MX or TXT records, because the CNAME replaces all lookups. (2) you cannot CNAME the apex (the zone root example.com) in strict DNS, because the zone root must have SOA and NS records. Cloud providers work around this with ALIAS or ANAME records (Route 53 Alias, Azure DNS) that look like CNAMEs but are resolved server-side.

MX — where mail goes. Each MX record has a priority (lower = preferred) and a hostname (not an IP; the hostname must itself have A/AAAA). Multiple MX records with different priorities are the backup pattern: 10 mail1, 20 mail2. Sending servers try lower priority first, fall through on failure.

NS and SOA — who is in charge. NS (name server) records say "these hosts are authoritative for this zone". SOA (Start of Authority) is one per zone and carries the zone's metadata: the primary nameserver, an admin email (with . replacing @, because @ has special meaning in DNS), a serial number (incremented on every zone change — secondaries use this to detect "do I need to refresh?"), and four timers: refresh (how often secondaries check for changes), retry (how fast to try again on failure), expire (secondaries stop answering after this), minimum TTL (negative caching duration for NXDOMAIN). Bumping the serial is how you "publish" a zone update.

TXT — arbitrary text, but actually a pile of conventions.
  • SPF (Sender Policy Framework): "v=spf1 include:_spf.google.com ~all" — "these hosts are allowed to send mail as my domain". Receivers check this to reduce spoofing.
  • DKIM: public key used to verify the signature on outgoing mail.
  • DMARC: policy that tells receivers what to do when SPF/DKIM fail (reject, quarantine, allow).
  • Domain verification — Google/AWS/etc. ask you to add a specific TXT record to prove you own the domain before they'll issue certs or grant API access.
  • Let's Encrypt DNS-01 challenge uses a TXT record to prove ownership.
PTR — reverse DNS (IP → name). Lives in a special zone in-addr.arpa (IPv4) or ip6.arpa (IPv6). PTR records only work if the owner of the IP (your cloud provider, typically) has configured them. Mail servers check reverse DNS as a spam signal — if your outbound SMTP IP doesn't have PTR matching your HELO name, a lot of providers tag your mail as spam.

SRV — service discovery, pre-Kubernetes. Format: _service._proto.name → priority weight port host. "Here's where to find XMPP for example.com, and on what port". Heavily used by Microsoft AD (_ldap._tcp.example.com), SIP/VoIP, and older service discovery. Kubernetes creates SRV records for every service (_http._tcp.my-service.my-namespace.svc.cluster.local) for this exact reason.

CAA — which CAs may issue certificates for your domain. A newer record (2013) that tells the TLS ecosystem "only Let's Encrypt may issue for example.com". Misissuance risk mitigation — if an attacker compromises a different CA, they still can't get a valid cert for your domain because publicly-trusted CAs check CAA before issuing.

TTL — the knob that controls cache pain. TTL on every record tells resolvers how long to cache the answer. Short TTLs (60s) let you change records quickly (emergencies, failover), but increase query load on your authoritative servers. Long TTLs (86400 = 1 day) are efficient but mean changes take a long time to propagate. The universal play before a planned migration: lower TTL to 60s a day in advance, do the migration, then raise back. For emergencies, you still have to wait out the old TTL at resolvers that already cached — DNS propagation delays are a classic production pitfall.

ConcernCannot name any DNS record types.
Mild ConcernKnows only A records.
MixedA and CNAME but limited on others.
Meets BarA, AAAA, CNAME, MX, NS, SOA, TXT with practical use cases.
Raises BarSRV, PTR, CAA; SOA fields (serial/refresh/retry/expire); TTL and caching; TXT uses (SPF, DKIM, DMARC, domain verification); DNS-based service discovery.


Q4 · Subnetting & Network Calculation   ⚪ LOW


Problem:   How many hosts are in a /23 network? What are the benefits of subnetting? A router has a /25 interface and a PC has a /24 — why can't they communicate?

REFERENCE 
# /23 usable hosts
32 - 23 = 9 host bits -> 2^9 = 512 addresses
Minus 2 (network + broadcast) = 510 usable

# Benefits
- Smaller broadcast domains
- Isolation / security
- Smaller routing tables
- Efficient IP allocation

# /25 router vs /24 PC mismatch
Different subnet masks => different ideas of what is "local".
The PC thinks more hosts are on its local subnet than the router
does; some traffic gets sent directly (ARP) instead of to the
gateway, breaking communication. Both sides must agree on mask.

🔍 DEEP DIVE — A SUBNET IS WHAT "LOCAL" MEANS

An IP address is 32 bits split into "network" and "host" portions. The subnet mask (or its shorthand, /N CIDR notation) tells you how many bits are network. A /24 means the first 24 bits identify the network and the remaining 8 identify hosts within that network. That split is what every networking decision on a host hangs on.

The calculation shortcut: hosts in a /N subnet = 2^(32-N) - 2. The minus 2 is because the all-zeros host address is the network address itself (not assignable) and the all-ones address is the broadcast address (reserved for "send to everyone on this subnet"). So /23 = 2^9 - 2 = 510, /24 = 254, /25 = 126, /30 = 2 (point-to-point links use /30 because you only need two hosts).

Why subnetting exists at all — four reasons:
  • Smaller broadcast domains. ARP, DHCP, and other layer-2 protocols broadcast to every host in a subnet. A flat /16 with 65k hosts would drown in broadcast traffic. Splitting into many /24s keeps that noise localized.
  • Security boundaries. Firewalls and ACLs operate on subnet granularity. Putting "database servers" in their own subnet lets you write "only app subnet can reach DB subnet on port 5432" — much cleaner than per-host rules.
  • Smaller routing tables. Routers don't need a route per host; they need a route per subnet. This is what made CIDR (Classless Inter-Domain Routing) a game-changer in the 90s — before it, the internet's routing tables were about to explode.
  • Efficient IP allocation. Before CIDR, you could only get /8, /16, or /24. A company that needed 500 hosts was forced to take a /16 (65k). CIDR lets them take a /23 (510) and everyone wins.
The mask-mismatch question tests layer-2 understanding. When a host wants to send a packet, it uses its own subnet mask to decide: "is the destination on my local subnet?". If yes, it ARPs for the destination's MAC address and sends directly. If no, it sends to its default gateway.

So: PC thinks it's on 192.168.1.0/24 (all of .1-.254 is local). Router thinks the same wire is 192.168.1.0/25 (only .1-.126 is local; the rest need to be reached via a different interface). When PC at .50 tries to reach .150:
  • PC says ".150 is on my local subnet", ARPs for it. Depending on ARP behavior, either nothing responds (packet dropped) or the wrong device answers (packet misrouted).
  • Even if the ARP succeeds and the packet lands at the router, the router says ".150 is not on my /25 local segment" and tries to route it elsewhere — likely back out the same interface or to an unexpected destination.
Fixing this means making both sides agree on the mask. Mask misconfigurations are a surprisingly common root cause of "works for some hosts, not others" production issues.

Special address ranges worth knowing (RFC 1918 private + reserved):
  • 10.0.0.0/8 — 16M addresses, most common for large corporate nets and cloud VPCs.
  • 172.16.0.0/12 — 1M addresses, 172.16.0.0 through 172.31.255.255.
  • 192.168.0.0/16 — 65k, home routers and small offices.
  • 127.0.0.0/8 — loopback (you only ever use 127.0.0.1, but the whole /8 is reserved).
  • 169.254.0.0/16 — "link-local" — when DHCP fails, hosts self-assign from here. AWS instance metadata lives at 169.254.169.254 (IMDSv2 endpoint); it works because every VPC routes this link-local address to the hypervisor.
  • 100.64.0.0/10 — Carrier-grade NAT space; increasingly used in cloud for shared services.
VLSM (Variable Length Subnet Masks) is the modern default — you can have a /16 at the top, split into /20s for sites, split into /24s for VLANs, and /30s for point-to-point links, all within the same VPC. Supernetting is the opposite: aggregate many small networks into one route advertisement so your upstream router has fewer entries.

IPv6 subnetting: addresses are 128 bits, convention is to allocate /64 per subnet (plenty of hosts forever), and sites typically get /48 or /56. You rarely hand-calculate hosts in IPv6 — the answer is always "essentially unlimited".

Q5 · TCP 3-Way Handshake   🟢 HIGH


Problem:   Explain the TCP 3-way handshake in detail. What happens at each step? What about connection termination?

REFERENCE 
# 3-way establishment
Client  --> SYN  (seq=x)                   Server
Client <--  SYN-ACK (seq=y, ack=x+1)       Server
Client  --> ACK  (ack=y+1)                 Server
# Connection ESTABLISHED

# 4-way termination
Initiator --> FIN           Peer
Initiator <-- ACK           Peer
Initiator <-- FIN           Peer
Initiator --> ACK           Peer
# Initiator enters TIME_WAIT (2 * MSL)

# Purpose
# - Synchronize sequence numbers for reliable delivery
# - Negotiate TCP options (MSS, window scaling, SACK)

🔍 DEEP DIVE — THE HANDSHAKE IS A STATE SYNC

The 3-way handshake does one essential job: agree on starting sequence numbers and TCP options before a single byte of application data flows. Every TCP byte is numbered; without a synchronized starting point, you can't detect duplicates, reorder segments, or ACK anything.

Step by step, with what's really happening:
  • Client → SYN (seq=x): "I want to talk. My starting sequence number is x." The client picks x randomly, not 0 — if it used 0, an attacker could forge packets claiming to be in the middle of any new connection. Randomized Initial Sequence Numbers (ISN) are a defense against off-path TCP injection. The SYN also carries TCP option proposals: MSS (max segment size this side can receive), window scale (multiplier for the 16-bit window field — needed for modern link speeds), SACK permitted (selective acknowledgment capability), timestamps.
  • Server → SYN-ACK (seq=y, ack=x+1): "Got it. My starting sequence is y, and I acknowledge x+1 (ready for the next byte after yours)." The server's sequence is also random. Server locks in its side of the negotiated options. At this point the server has a half-open connection in its SYN_RCVD state.
  • Client → ACK (ack=y+1): "Acknowledging your y." Connection is now ESTABLISHED on both sides. Any data can piggyback on this ACK — the client doesn't have to wait another round trip to start sending. TCP Fast Open goes further: with a prior cookie, the client can put application data in the initial SYN, saving another RTT for subsequent connections.
Why it's 3 steps, not 2: if the client just sent "SYN, my seq is x" and the server replied "OK, acknowledged", there's no way to be sure the server's own seq got through. The third ACK confirms the client received the server's sequence. In general, both sides must confirm they received the other's ISN — that requires three messages.

Termination is 4-way because TCP is full-duplex. Each side closes its outbound stream independently. Client sends FIN ("I'm done sending"), server ACKs, server sends its own FIN when its application decides to close ("I'm done too"), client ACKs. The two FINs can arrive at different times because each side may still have data to deliver after receiving the peer's FIN. If both sides close simultaneously, you can see a simultaneous close (3-way).

TIME_WAIT is the most operationally painful TCP state. After sending the final ACK, the initiator (typically the client that called close() first) enters TIME_WAIT for 2*MSL (Maximum Segment Lifetime, usually 60-120 seconds). Purpose: (1) ensure the final ACK reaches the peer — if it's lost, the peer retransmits its FIN and TIME_WAIT can ACK it again; (2) make sure old duplicate packets from this connection don't bleed into a new connection reusing the same 4-tuple.

On a high-traffic client that opens and closes many short connections to the same server (typical of poorly-configured reverse proxies), you can hit the local port exhaustion problem: every TIME_WAIT ties up a (source IP, source port, dest IP, dest port) tuple. With a single local IP and a single destination, you have ~28,000 ephemeral ports; at 10k/s short connections you exhaust ports in seconds. The fixes:
  • Connection reuse / HTTP keep-alive — don't open a new TCP connection per request.
  • SO_REUSEADDR / SO_REUSEPORT — let new sockets bind over TIME_WAIT ones (safely, when compatible).
  • net.ipv4.tcp_tw_reuse sysctl — allow reusing sockets in TIME_WAIT when the timestamp option confirms it's safe (preferred over the unsafe tcp_tw_recycle).
The security angle: SYN floods. An attacker sends many SYNs with spoofed source IPs; the server allocates resources for each in SYN_RCVD and waits for the third ACK that never comes. Eventually the server's connection backlog fills up and real clients can't connect. SYN cookies are the defense: the server doesn't actually allocate state on receiving a SYN. Instead, it crafts a SYN-ACK with a cookie (a hash of connection info + secret) as its ISN. If the client is real and replies with an ACK, the server can validate the cookie and reconstruct the connection state. Only legitimate clients cost the server memory.

What the interviewer really wants: show that you know the handshake is about synchronization + negotiation, not just "three packets". Mention sequence randomization (security), option negotiation (MSS, window scale), and TIME_WAIT (operations) — each is an invitation to a deeper follow-up.

Q6 · OSI Model   🟡 MEDIUM


Problem:   Explain the OSI model. What are the 7 layers and what happens at each?

OSI LAYERS 
7  Application    HTTP, DNS, SMTP, SSH
6  Presentation   TLS, compression, encoding
5  Session        session mgmt, dialog control
4  Transport      TCP, UDP -- segments, ports
3  Network        IP -- packets, routing
2  Data Link      Ethernet, MAC, ARP -- frames, switches
1  Physical       cables, signals, bits

# Troubleshooting by layer
L1: check cables, interface lights
L2: check ARP, duplicate MACs
L3: check routing table, default gateway
L4: check ports, firewall, conntrack
L7: check application logs, curl

🔍 DEEP DIVE — LAYERS ARE ENCAPSULATION BOUNDARIES

The OSI model is a conceptual framework, not a literal implementation. It was designed by committee in the 80s as a "what if we standardized everything?" reference. The actual internet runs on the TCP/IP model (4 layers: Link, Internet, Transport, Application), which collapses OSI 5-7 into one ("Application"). But OSI is still the lingua franca for troubleshooting — when someone says "this is a layer 3 problem", they mean "it's an IP/routing issue, not DNS or TCP".

The core idea is encapsulation. Each layer adds its own header (and sometimes trailer) around the data from the layer above, then hands it to the layer below. When a packet arrives, each layer strips its header and passes the payload up. Like nested envelopes. The practical consequence: each layer only talks to its peer layer on the other machine, and doesn't care about what's inside the payload or how the layers below deliver it.

Layer 1 — Physical. Literal bits on a wire (or photons on fiber, or radio waves on WiFi). Hubs and repeaters operate here; they don't care about anything above bits. Troubleshooting cues: cable unplugged, no link light, mismatched duplex, NIC errors in ip -s link.

Layer 2 — Data Link. Frames with MAC addresses; scope is a single physical network segment. Ethernet, WiFi (802.11), VLANs, ARP live here. Switches operate at L2 — they learn which MAC is on which port and forward frames. ARP is the L2-to-L3 bridge: "who has IP 10.0.0.1? Tell me your MAC." Every host maintains an ARP cache; corrupted ARP is a classic cause of "I can't reach my gateway" issues (arp -a, ip neigh).

Layer 3 — Network. Packets with IP addresses; scope is end-to-end across any number of networks. Routers operate here; they read the destination IP and consult their routing table to decide which interface to send out. ICMP (used by ping, traceroute, and error messages like "host unreachable") is L3. IPsec is L3.

Layer 4 — Transport. Segments with ports. TCP and UDP live here. Firewalls that filter by port (security groups, iptables on port) are L4. L4 load balancers (AWS NLB, HAProxy in TCP mode) distribute by TCP/UDP tuples without inspecting application data — they're fast, work with any protocol, and are oblivious to headers.

Layer 5 — Session. In theory: dialog control, checkpoint/restart, session tokens. In practice: mostly folded into the application layer today. NetBIOS, RPC, and SOCKS are canonical examples. You rarely distinguish L5 from L7 in modern stacks.

Layer 6 — Presentation. In theory: data format translation (ASCII/EBCDIC), compression, encryption. In practice: TLS is often called a "layer 6" concept but it really operates between L4 and L7 — it runs on top of TCP and provides an encrypted byte stream to the application. The "layer 6" label is a teaching convenience.

Layer 7 — Application. HTTP, DNS, SMTP, SSH, BGP (yes, BGP is an application running over TCP). L7 load balancers (ALB, CloudFront, nginx) read headers, URL paths, and cookies to route — much more powerful than L4, but require terminating the connection to inspect. WAFs (web application firewalls) operate at L7.

The TCP/IP model vs OSI: TCP/IP merges L1+L2 into "Link" (the stack doesn't care about the cable vs WiFi distinction), L3 is "Internet", L4 is "Transport", and L5+L6+L7 become "Application". Most real engineering uses TCP/IP's granularity. You'll hear both.

Why the layering actually matters in production: when something breaks, the right question is "which layer is this?". Ping works but SSH fails = L3 OK, L4 or L7 problem (firewall? service down?). DNS fails but ping by IP works = L3 OK, L7 problem (resolver down). Can't ping the gateway = L2 problem (ARP) or L3 misconfig. Interface shows no carrier = L1 problem (cable, switch port). Naming the layer focuses where to look next.

Where TLS sits — the question that trips people up: TLS runs over TCP (so above L4) but under the application protocol (so below L7). Some teachers call it "layer 6" or "5-6"; others (including the IETF) say "TLS is between 4 and 7". The pragmatic answer: "TLS sits on top of TCP and provides an encrypted byte stream to the application".

🔍 DEEP DIVE — TWO FAMILIES OF ROUTING ALGORITHMS

A routing protocol is how routers tell each other "here's how to reach network X". The internet is ultimately a forest of routing tables, kept in sync by protocols that exchange reachability information. Two algorithmic families explain almost every protocol: distance-vector and link-state. A third, path-vector, is essentially distance-vector with extra policy metadata.

Distance-vector (RIP, EIGRP family). Each router tells its neighbors "I can reach network X in N hops". Neighbors update their own tables and propagate. Simple, minimal state, but slow to converge after a topology change (the "count-to-infinity" problem: router A hears from B that "X is 2 hops", so A says "I can reach X via B in 3 hops"; if X dies, it takes many rounds of exchange for A and B to believe it's gone). RIP maxes out at 15 hops and uses simple hop count as the metric — legacy, tiny networks only.

Link-state (OSPF, IS-IS). Every router floods its local connectivity (which neighbors are reachable and at what cost) to every other router in the area. Each router independently builds a complete map of the network topology and runs Dijkstra's shortest path algorithm to compute routes. Far more state, far more memory, but much faster convergence: when a link goes down, one flood update reaches everyone, and everyone recalculates.

OSPF is the default choice for medium/large internal networks because:
  • Fast convergence (seconds, vs minutes for RIP) — critical when a link fails during business hours.
  • Area hierarchy — OSPF lets you split the network into areas connected to a backbone (area 0). Routers only carry detailed state for their own area; other areas are summarized. Keeps the Dijkstra computation tractable and limits flooding scope.
  • Cost-based metric — you can set per-link costs (typically inversely proportional to bandwidth) and steer traffic explicitly.
  • Open standard — works across vendors. EIGRP is Cisco-proprietary (though now open-ish); IS-IS is comparable to OSPF and preferred in very large ISP backbones, but OSPF has more tooling and familiarity.
Path-vector — BGP. Between Autonomous Systems (ISPs, cloud providers, large enterprises), you use BGP. Instead of hop count or link cost, BGP exchanges the full AS path to each network ("to reach X, go through AS 65001, then AS 65002, then it's theirs"). This serves two purposes: (1) loop prevention (if your own AS number appears in the path, don't use that route), and (2) policy-based routing — ASes can refuse to route through competitors, prefer paid transit over free peering, apply different metrics for different customers, etc. BGP isn't about finding the shortest path; it's about enforcing business relationships.

Why BGP is inappropriate for internal networks: it's slow (convergence in minutes), chatty (full tables are hundreds of MB), and policy-complex. For your corporate LAN, you just want "find the best path fast". OSPF does that.

Why this is marked LOW for AFT: as an SDE, you'll rarely configure a routing protocol. But you may hit routing questions in a debugging context — "traffic from us-east-1 to ap-south-1 is slow" could be a BGP path issue on AWS's backbone, and knowing the vocabulary lets you read their network post-mortems. For cloud work, the VPC route tables you edit are static routing — no protocol negotiation, just hand-written "send 0.0.0.0/0 to this IGW" entries.

Modern layer on top — SDN and overlay networks. Cloud data centers increasingly use SDN (software-defined networking) where the control plane is centralized and the physical topology is hidden. VXLAN, Geneve, and similar overlays let you build a virtual L2 network on top of IP. You'll hear less about traditional OSPF/BGP and more about "this route was installed by the controller".

"Connection timed out"  = no response in window (firewall drop, down host)

🔍 DEEP DIVE — THE THREE ERRORS TELL YOU WHICH LAYER TO LOOK AT

The key insight: "no route to host", "connection refused", and "connection timed out" are three entirely different failures that sound similar but point at different layers. Getting this distinction right is the whole interview-worthy moment.

"No route to host" (EHOSTUNREACH) — Layer 3 problem. Your kernel couldn't find a path. Either your routing table has no entry for the destination (no default gateway, or the default gateway itself unreachable), or the ARP request for the gateway got no reply, or a router along the path sent back an ICMP "host unreachable" message. The destination service isn't even in the question — you never got close enough to test it.

"Connection refused" (ECONNREFUSED) — Layer 4 problem, but a good one. Your TCP SYN reached the destination host, and the host's kernel actively rejected it by sending a TCP RST. The rejection means nothing is listening on that port. The host is up and reachable; the service is down or bound to a different port. This is often a debugging relief — you've eliminated network as a cause.

"Connection timed out" (ETIMEDOUT) — ambiguous, but usually a firewall. You sent a SYN, heard nothing back, kept retrying, gave up after ~75 seconds (kernel default). Most common causes in order: (1) a firewall in the path silently dropped your packet (security groups, iptables DROP, corporate proxy); (2) the destination host is completely offline (no one to reply at all); (3) asymmetric routing (your SYN arrived, their SYN-ACK didn't come back). "Dropped" not "refused" is what firewalls do by default because silent drops slow down attackers (they have to wait for their own timeout instead of getting fast RST feedback).

The systematic diagnostic ladder — walk from your own machine outward:
  1. Do I have an IP? ip addr — if my interface has no address, nothing else matters. Typical fix: DHCP, dhclient eth0, check cable/WiFi.
  2. Do I have a route? ip route — must show a default route (default via 10.0.0.1 dev eth0). No default = I can only reach my local subnet.
  3. Can I reach my gateway? ping -c 2 $(ip route | awk '/default/ {print $3}') — if not, it's ARP/L2 (wrong VLAN, unplugged, bad MAC) or the gateway itself is down.
  4. Does DNS work? dig amazon.com — a timeout or SERVFAIL here is an L7 DNS issue, not a routing issue. dig @1.1.1.1 amazon.com bypasses the local resolver to isolate.
  5. Can I reach the destination IP directly? ping <resolved-IP> — bypasses DNS completely. ICMP is often blocked, so silence here isn't conclusive; try nc -zv $IP 443 instead (TCP probe).
  6. Where along the path does it die? mtr -n $IP or traceroute -T $IP — the last hop that responds is usually just before the problem. Asterisks all the way through could just mean ICMP filtering; interpret carefully.
  7. Is my own firewall blocking? iptables -L -v -n, or on cloud: check security groups and NACLs. "outbound allowed" isn't always true — egress rules can block.
  8. Is the destination's firewall blocking? You usually can't see this directly. Symptom: port probe (nc -zv) times out but you know the service is running. Ask the destination owner to confirm they accept your source IP.
  9. Is the destination service actually up? If nc shows "connection refused" or succeeds but then reads zero bytes, the service is down or misconfigured (wrong bind address, 127.0.0.1 only).
The AFT-flavor escalation: "works from my laptop but fails from the EC2 instance". Isolate the difference by testing curl -v from both, compare network paths (mtr), compare source IPs (NAT gateway?), compare security groups and route tables, check if you're in a public vs private subnet. Cloud debugging adds VPC route tables, security groups (stateful, L4), NACLs (stateless, L3/L4), and endpoint policies as additional filtering layers. A single missing route in a VPC can produce exactly this symptom.

One subtle trap: the error message your application shows isn't always the error the kernel returned. curl and wget often print "Could not resolve host" for DNS failures, "Connection timed out" for firewall/reachability, "Connection refused" when the port is closed — read the exact wording. Different languages and libraries have different translations, but the kernel syscall return value (-ENETUNREACH, -EHOSTUNREACH, -ECONNREFUSED, -ETIMEDOUT) is the ground truth.

🔍 DEEP DIVE — PACKET LOSS HAS A LAYER AND A LOCATION

"Intermittent connectivity" is one of the most common support tickets you'll see. The wide phrasing is a signal — the reporter knows something's wrong but can't localize it. Your job is to localize the loss in both layer and location before you try to fix anything.

Step 1 — confirm loss is real, not perceived. Users often report "slow" or "flaky" when the problem is actually a specific endpoint, a specific time of day, or an application-layer issue. Reproduce with hard data: ping -c 1000 -i 0.2 $TARGET gives you a loss percentage over a few minutes. Run from multiple locations (your laptop, a canary host near the service, a host far away) — if only one location sees loss, the problem is path-specific.

Step 2 — locate the lossy hop. mtr is the tool. It combines ping and traceroute: continuously probes each hop along the path and shows per-hop loss and latency. The classic pattern:
  • Loss starts at hop N and continues through the rest = the problem is at hop N or that router is CPU-limited for ICMP replies but forwards fine. Check the hop after (if it's your own infrastructure, log into it).
  • Loss at hop N but 0% after = that router rate-limits ICMP replies (common for backbone routers). It's not actually losing your real traffic — only its ICMP responses. Harmless; ignore.
  • Loss only at the destination = the last mile (the server, its host's NIC, its hypervisor, its load balancer).
  • Loss across multiple specific hops, correlated in time = upstream network congestion or BGP path flapping.
Step 3 — check the interface on each end. ip -s link show eth0 shows RX/TX drops and errors. Any non-zero counters (especially RX-DRP or RX-ERR growing) is a local cause: NIC saturated, kernel ring buffer too small, or physical layer issues. ethtool -S eth0 gives vendor-specific counters that are often more informative (rx_no_buffer_count, tx_hw_errors, rx_csum_offload_errors). On cloud: ethtool -S on an ENA-enabled EC2 instance shows AWS-specific counters like bw_in_allowance_exceeded — hitting instance bandwidth limits can present as packet loss.

Step 4 — check TCP's own view. ss -ti on an active connection shows you retransmits, RTO, CWND, and congestion window state per connection. A rising retrans counter during normal load means TCP is seeing loss at the application layer. nstat or /proc/net/snmp (TcpRetransSegs, TcpInSegs) give system-wide retransmit rates. Retransmit rate above ~0.5% is noticeable; above 2% causes serious slowdown because TCP keeps backing off.

Step 5 — MTU and Path MTU Discovery. If large packets drop but small ones succeed, you've got an MTU problem. Default Ethernet is 1500 bytes; some VPN tunnels, VXLAN overlays, or misconfigured links have smaller MTUs. If ICMP "fragmentation needed" messages are blocked by a firewall, PMTU discovery breaks and you get a black hole — large packets silently dropped. Diagnostic:
  • ping -M do -s 1472 $TARGET — no-fragment bit set, payload 1472. Success = MTU ≥ 1500 end-to-end. If it fails, decrement until you find the ceiling.
  • Fix: lower MTU on your interface (ip link set eth0 mtu 1400), enable TCP MSS clamping on your firewall, or unblock ICMP type 3 code 4.
Step 6 — packet capture for root cause. tcpdump -i eth0 -w /tmp/cap.pcap host $TARGET for a few minutes, pull to your laptop, open in Wireshark. Wireshark's "Expert Info" pane highlights retransmissions, out-of-order, zero-window, and dup ACKs — these paint a picture of where in a TCP conversation loss happened. Capturing on both ends simultaneously is the gold standard; comparing what each side sent vs received pins down the direction and location of loss.

Step 7 — bandwidth and buffer tuning. On a fat-pipe WAN link (cross-region), default TCP buffers are too small; TCP can't keep enough data in flight to saturate the link. sysctl net.core.rmem_max and net.ipv4.tcp_rmem set receive buffer limits. On servers doing high-throughput work, bumping these is standard tuning. iperf3 measures achievable throughput between two hosts under ideal (no other traffic) conditions — use it to prove "the link can do 10 Gbps but my app only does 1 Gbps" before tuning.

The overarching mental model: loss happens at one of four places:
  • The sending host (buffer overflow, NIC error, cgroups limiting bandwidth).
  • Some network hop in between (congested link, broken router, rate-limiting device, MTU mismatch).
  • The receiving host (buffer overflow, NIC errors, kernel dropping due to conntrack table full).
  • The application layer (app not reading fast enough so TCP window closes, then "loss" is really backpressure).
Narrowing the diagnosis to one of these four categories is the real deliverable.

🔍 DEEP DIVE — TUNNELS ARE PORTS OVER A SECURE SESSION

An SSH tunnel is nothing more than "I've already authenticated a secure channel to this remote host — let me carry extra TCP connections inside it". Once you grasp that framing, -L vs -R vs -D become about which direction the tunneled connection flows and where the listener opens.

-L localport:targethost:targetport (Local forward) — opens a listener on YOUR machine, tunnels to the remote side, then the remote side opens a TCP connection from the remote host to targethost:targetport. Think of it as "exposing a remote service locally". The classic use case: your production DB is inside a private VPC, only the bastion host can reach it. You run ssh -L 3306:prod-db.internal:3306 bastion. Now you point mysql -h 127.0.0.1 at your local port; the traffic tunnels over SSH to the bastion, and the bastion opens a fresh TCP connection to the DB. From the DB's perspective, the connection is coming from the bastion, not from you — this is both useful (ACLs just need to allow the bastion) and sometimes confusing (DB logs show the bastion as source).

-R remoteport:targethost:targetport (Remote forward) — opens a listener on the REMOTE machine, tunnels back to your side. Think of it as "exposing a local service remotely". Use case: you're running a dev server on your laptop on port 3000, and you want a colleague's server (or a webhook tester) to reach it. ssh -R 8080:localhost:3000 remote makes port 8080 on remote forward to your laptop's port 3000. This is the primitive behind tools like ngrok — a public relay + reverse tunnel to your local dev box.

-D localport (Dynamic, SOCKS proxy) — opens a SOCKS proxy listener on your machine; any TCP connection you route through that SOCKS proxy is tunneled to the remote side and fanned out from there. Unlike -L which hardcodes one target, -D lets the client specify the target per-request. Use case: browsing as if from the bastion — configure your browser SOCKS proxy to 127.0.0.1:1080 and every page load goes out from the bastion's IP. This is how security researchers / travelers route web traffic through a trusted exit point.

Jump hosts / bastion pattern. In AFT-scale infrastructure, production hosts are in private subnets with no direct SSH from the internet. The access pattern is laptop → bastion (public) → target (private). The old way: SSH to bastion, SSH again from there. The modern way: ssh -J bastion target (ProxyJump). The client opens a TCP tunnel to bastion, then negotiates the SSH protocol with target through that tunnel — the target authenticates you directly, end-to-end, with your key never touching the bastion. This is much more secure than agent forwarding (see below).

~/.ssh/config is where this all gets tidy. Instead of long commands, you write once and reference by nickname. Example: 
Host bastion
    HostName bastion.prod.example.com
    User ramya
    IdentityFile ~/.ssh/id_ed25519_prod

Host prod-*
    ProxyJump bastion
    User ramya
    IdentityFile ~/.ssh/id_ed25519_prod
    ServerAliveInterval 60
    ControlMaster auto
    ControlPath /tmp/ssh-%h-%p-%r
    ControlPersist 10m
Then ssh prod-db01 automatically goes through the bastion, reuses the connection (ControlMaster), and keeps it alive.

Agent forwarding (-A) is dangerous and often misused. Agent forwarding means "let the remote host ask my local SSH agent to sign things for it". It's convenient — you can SSH from the bastion to the target without putting keys on the bastion. But anyone with root on the bastion can hijack your agent socket and authenticate as you to any host your keys reach. ProxyJump is safer: the client talks to the target directly through the tunnel; the bastion never sees any key material. Prefer -J; avoid -A.

Reliability: autossh. A plain SSH tunnel dies when the TCP connection breaks (network blip, laptop sleep). autossh -M 20000 -L ... wraps SSH with health monitoring and reconnects automatically. Useful for long-running dev tunnels or persistent reverse tunnels.

When SSH tunneling is the wrong answer: if you need a many-host, many-service, always-on network between environments, a VPN (WireGuard, AWS Site-to-Site, Tailscale) is the right abstraction — same outcome, less operational fuss. SSH tunnels are perfect for ad-hoc, one-off access; VPNs are for continuous integration. For AWS-native: SSM Session Manager replaces SSH entirely for many use cases, tunneling through the agent on the instance (no inbound port 22 needed).

    Executes JS, paints, interactive

🔍 DEEP DIVE — THE INDUSTRY'S FAVORITE WHITEBOARD QUESTION

This is the question that separates candidates. The full journey touches every layer of the stack, and interviewers love it because they can drill down wherever your answer is weakest. A well-organized answer is layered: name each phase first, then offer to go deeper on any part. Here's what "deep" looks like at each layer.

Phase 1 — Before DNS: cache layers. The browser has its own DNS cache (see chrome://net-internals/#dns), which has a per-entry TTL. If missing, it asks the OS. The OS consults /etc/nsswitch.conf (on Linux) or equivalent to decide the lookup order — typically /etc/hosts first, then the system resolver cache (systemd-resolved, nscd, or similar), then DNS over the network. A stale /etc/hosts entry can short-circuit everything and is a classic "DNS isn't resolving correctly" red herring.

Phase 2 — DNS resolution. The OS sends a query to its configured recursive resolver (from /etc/resolv.conf, often your ISP's or a public one like 1.1.1.1/8.8.8.8). If the resolver hasn't cached the answer, it walks the hierarchy:
  • Asks a root server (there are 13 logical root server clusters globally; the resolver has hardcoded hints).
  • Root replies "I don't know amazon.com, but I know the nameservers for .com".
  • Recursive resolver asks .com nameservers. They reply with the authoritative nameservers for amazon.com.
  • Recursive resolver asks those nameservers for www.amazon.com. They return the A record (or a CNAME pointing at a CDN like d3ag4hukkh62yn.cloudfront.net, which the resolver follows).
This whole process happens in ~20-50ms if caches are cold, microseconds if anything is cached. DNSSEC adds signature validation at each step (rarely breaks client-visibly but protects against cache poisoning).

Phase 3 — TCP to the resolved IP. The browser calls connect() with the server IP and port 443. The kernel routing table is consulted to pick an interface. If the destination isn't on the local subnet, an ARP request finds the MAC of the default gateway. The 3-way handshake begins (see Q5). For performance, browsers maintain a connection pool and often have a TCP connection already open to popular sites via HTTP/2's single-connection multiplexing.

Phase 4 — TLS handshake. Only if HTTPS. The client sends ClientHello with: supported TLS versions, cipher suites, SNI (Server Name Indication — the hostname, which is how a single IP can serve certs for multiple domains), and ALPN protocols (h2, h3, http/1.1). The server responds with ServerHello picking one cipher, its certificate chain (leaf + intermediates, without the root), and if using ECDHE, a signed ephemeral key share. The client verifies the chain up to a trusted root CA (in the OS or browser trust store), checks the hostname matches the cert's SAN list, and generates a shared symmetric key via ECDHE (Perfect Forward Secrecy: past sessions aren't decryptable even if the server's long-term key is stolen). All subsequent traffic is encrypted with the symmetric key. TLS 1.3 compresses all this to one round trip (vs TLS 1.2's two); 0-RTT data is possible with prior session tickets.

Phase 5 — HTTP request. Inside the TLS channel, the browser sends: GET / HTTP/2, Host: www.amazon.com (crucial for virtual hosting), User-Agent, Accept, Accept-Encoding: gzip, br (compression methods), Cookie, and a pile of others. HTTP/2 multiplexes many requests onto one TCP connection; HTTP/3 runs over QUIC (UDP) to avoid head-of-line blocking.

Phase 6 — The server side. The request typically hits a CDN edge first (CloudFront, Akamai); if the resource is cacheable and fresh, the CDN responds directly without touching origin. For dynamic content, the CDN forwards to an ALB/NLB which picks a backend. The backend might hit authentication, then business logic, then a database or a cache. The response is written back up the chain; the CDN may cache it. Total: anywhere from 10ms to several hundred depending on cache hits.

Phase 7 — Browser rendering. The browser starts parsing HTML as bytes stream in (streaming parse). As it encounters <link rel="stylesheet"> and <script> tags, it fires more requests (sometimes in parallel, sometimes render-blocking). The DOM is built; CSS is applied to build the CSSOM; they combine into the Render Tree. JavaScript runs and may modify any of these. The browser does layout (where does each box go?), paint (which pixels get which color?), and composite (GPU-accelerated layer merging).

The performance measurements hidden in the question — timing each phase is what Chrome DevTools → Network → Timing shows: DNS Lookup, Initial Connection (TCP), SSL (TLS), Waiting (TTFB = server thinking time), Content Download. curl -w with time_namelookup / time_connect / time_appconnect / time_starttransfer / time_total gives you the same from the command line — essential for debugging "which part is slow".

The senior-level move is to volunteer the failure modes at each step: DNS can resolve to stale IPs if TTLs are long; a TCP SYN can be dropped; TLS cert validation can fail; the server can return 5xx; the browser can block on a slow render-blocking script. Offering "I can go deeper on any of these" invites the interviewer to pick, which lets them see what they want without you guessing wrong.

"I can't SSH" is really seven different failures wearing the same sweater. Walk outward from your client, and you'll find the break:

1. DNS. Is the hostname resolving? dig or host the name. If it returns nothing or the wrong IP (stale cache, bad /etc/hosts entry), everything downstream fails weirdly. SSH will print "Could not resolve hostname".

2. Network reachability to port 22 (or whatever SSH runs on). nc -zv host 22 is the isolation test — it's a TCP connect with no protocol; if this times out, the problem is network, not SSH. Distinguish:
  • Timeout = firewall silently dropping, or host is offline. Could be security group, NACL, iptables DROP, corporate proxy.
  • Connection refused = you reached the host but nothing is on port 22. sshd isn't running, or listening on a different port/interface.
  • No route to host = L3 problem (see Q8).
3. sshd is running but misconfigured. On the server side (via console/IPMI if SSH is gone): systemctl status sshd, journalctl -u sshd -n 50, check ss -tnlp | grep :22. If Listen is bound to 127.0.0.1 instead of 0.0.0.0, you can only SSH from the box itself. /etc/ssh/sshd_config directives to check: Port, ListenAddress, AllowUsers, AllowGroups, DenyUsers, PermitRootLogin, PasswordAuthentication, MaxSessions, MaxStartups (floods reject when the limit is hit), ChrootDirectory (can break sftp-only setups).

4. Authentication — keys or password. ssh -vvv user@host shows the auth negotiation live. Frequent issues:
  • Key file permissions wrong. chmod 600 ~/.ssh/id_*, chmod 700 ~/.ssh. SSH refuses to use keys that are group-readable (paranoid but correct).
  • Server-side authorized_keys wrong permissions. Must be 600, owned by the user, home dir itself must be 750 or stricter. auth.log will show Authentication refused: bad ownership or modes.
  • Key not in agent. ssh-add -l to check; ssh-add ~/.ssh/id_ed25519 to add.
  • Algorithm mismatch. Very old servers reject modern key types; very new servers may reject ancient SHA-1 RSA. -vvv shows the negotiation; try -o PubkeyAcceptedKeyTypes=+ssh-rsa as a temporary workaround.
5. User account state. The user exists (getent passwd user) but is locked (passwd -S user shows L), has a nologin shell, or is missing from the AllowUsers directive. sudo -u user whoami tests whether the account is functional at all.

6. Host key changes — the "WARNING" screen. If SSH prints REMOTE HOST IDENTIFICATION HAS CHANGED!, your ~/.ssh/known_hosts has a stale entry (common after rebuilding a server with the same hostname). This is correct by design — SSH is warning that the host might be spoofed. Fix: ssh-keygen -R hostname to remove the stale entry, then reconnect and accept the new key (after verifying the fingerprint out-of-band if it's a production host).

7. Out-of-band access when SSH is gone entirely. AFT reality: you broke SSH on a production host by misconfiguring sshd_config and reloading. Now you can't get in to fix it. The options: AWS EC2 Instance Connect / SSM Session Manager (agent-based, no port 22 needed), serial console, IPMI / iDRAC for physical hosts, user data / cloud-init script that runs on next reboot. Always preserve at least one of these before touching sshd_config. The canonical safe pattern: open a second SSH session before editing sshd_config, then test the config (sshd -t), reload, and verify the second session still works and that you can open a third before closing the first.

The "MaxStartups" trap: if many users SSH at once (or a scanner hits you), sshd starts randomly dropping new connections long before any authentication fails. Symptoms are flaky "sometimes works, sometimes times out during banner". Tune MaxStartups 100:30:200 (start dropping at 100 concurrent unauthenticated, 30% drop rate, hard cap at 200).

Debugging the verbose output: ssh -vvv output is long, but the first useful line is usually debug1: Authentications that can continue: — it tells you what the server is offering and what you've tried. Look for debug1: Server accepts key: / Authenticated to (success) vs Permission denied (publickey,password). (failure). If it never gets past "Connection established" you're in network territory; if it authenticates but disconnects, you're in shell/PAM/policy territory.

🔍 DEEP DIVE — LOAD BALANCERS SOLVE TWO PROBLEMS AT ONCE

A load balancer exists because of two independent concerns that happen to share a solution: (1) one server isn't enough — you need to spread load across many, and (2) servers fail — you need a stable entry point that survives individual failures. A load balancer is the "stable IP / DNS name" that clients see; behind it, instances come and go, scale up and down, without anyone noticing.

L4 vs L7 is the first decision.
  • L4 load balancers (AWS NLB, HAProxy in TCP mode, older hardware LBs) operate at the transport layer: they see only TCP/UDP 5-tuples (source IP, source port, dest IP, dest port, protocol). They don't terminate the connection — they forward packets or bridge TCP flows. Because they don't parse application data, they're protocol-agnostic (any TCP works: databases, Redis, custom binary protocols, WebSocket) and extremely fast (packet-level, nanoseconds). Downside: they can't route by URL path, can't modify headers, can't understand HTTP.
  • L7 load balancers (AWS ALB, nginx, Envoy, HAProxy in HTTP mode) terminate the client connection, read the HTTP request, make routing decisions on path / host / headers / cookies, and open a fresh connection to the chosen backend. They can rewrite URLs, add security headers, serve error pages, do authentication. Downside: HTTP-only, more CPU per request, more configuration.
  • Rule of thumb: HTTP → ALB/L7; raw TCP or absolute lowest latency → NLB/L4; both if you want L4 to front L7 for specific workloads.
The routing algorithms each make a tradeoff:
  • Round-robin: simplest, but ignores backend load. A struggling backend gets the same traffic as a healthy one.
  • Least connections: sends new requests to the backend with the fewest active. Good default for long-lived or variable-duration requests.
  • IP hash / source hash: the same client always goes to the same backend. Cheap way to get session affinity without cookies. Breaks on NAT (all clients behind a NAT share an IP).
  • Weighted: for heterogeneous fleets (some bigger instances get more traffic) or for canary deploys (route 5% to the new version).
  • Consistent hashing: used when backends have cached state. A key (session ID, user ID, request URL) maps to a backend; adding/removing backends only re-routes a small fraction. Essential for cache servers (memcached, Redis cluster); irrelevant for stateless app servers.
Health checks are what make "high availability" real. The LB periodically probes each backend (TCP connect for L4, HTTP request for L7). Backends failing N consecutive checks are ejected from the pool; they come back when they pass M consecutive checks. Tune the thresholds: too aggressive and flapping ejects healthy-but-slow backends; too loose and users see errors on dead backends. Depth of the check matters — checking /healthz that just returns 200 doesn't catch "DB is down but my process is up". A proper health check verifies downstream dependencies too (but not so aggressively that it itself takes down the service).

Sticky sessions — the pattern that doesn't scale. If your app stores session state in-memory per backend, you need to send the same user back to the same backend every time. ALB does this with a cookie (AWSALB); nginx with ip_hash or a cookie. The real fix is to make the app stateless: store sessions in Redis/DynamoDB/a JWT, and any backend can serve any request. Sticky sessions are a band-aid; persistence-in-Redis is the cure.

TLS termination vs passthrough. Terminate at the LB (decrypt at LB, forward plaintext to backends): backends don't need cert management, and the LB can inspect headers (required for L7). Downside: traffic between LB and backend is unencrypted — fine in a private VPC, not fine across the internet. Passthrough (LB forwards the encrypted bytes to the backend, which terminates TLS): end-to-end encryption, but the LB can't make L7 routing decisions. ALB only does termination; NLB can passthrough. Many production setups terminate at the LB and also re-encrypt to backends for defense-in-depth.

Connection draining (deregistration delay). When you remove a backend from the pool (deploy, scale down, health check failure), the LB stops sending new connections to it but keeps existing ones open for a grace period (default 300s on AWS). This is what makes rolling deployments possible without dropping requests. Tune it to your longest request time; too short and long-running requests get chopped; too long and deploys are slow.

DNS-based / global load balancing. Route 53 latency-based routing and similar services don't have a real LB — they return different IPs from DNS based on client location, so a user in Tokyo gets your ap-northeast-1 LB IP and a user in Dublin gets eu-west-1. Works across regions; limitation: DNS caching (TTL) delays failover. Anycast is the sibling technique at the routing layer: one IP address, announced from many locations; BGP decides which location is "closest" per client. Used by CloudFront, Cloudflare, Google DNS.

The AFT-relevant insight: in a fulfillment environment, you'll encounter LBs as the first suspect during incidents. "The service is returning 502s" often means the LB can't reach backends (are they healthy?) or backends are returning bad responses (502 from LB upstream = "something's wrong server-side, check app"). Knowing the difference between 502 (bad response from upstream), 503 (LB itself overloaded or no healthy backends), and 504 (upstream timeout) immediately localizes the fault.

Q14 · HTTP Status Codes (detailed)   🟢 HIGH


Problem:   Name the HTTP status code categories (2XX, 3XX, 4XX, 5XX) and give specific examples with when they occur.

🔍 DEEP DIVE — STATUS CODES AS OPERATIONAL SIGNALS

This question is the operational cousin of Q1 — where Q1 focused on knowing the codes, this one is about what they tell you about your system's health. Same codes, different lens.

2xx/3xx vs 4xx vs 5xx as a health signal. In a production dashboard, the ratio of these three buckets is your availability SLO. A healthy system is mostly 2xx with a small amount of legitimate 3xx (redirects) and 4xx (users making bad requests). When 5xx climbs, you're on fire. When 4xx climbs sharply, something changed — a client deployed a new version with bugs, or you deployed stricter validation, or an attacker is probing. Both directions are meaningful signals.

The 5xx category is the alerting target. Every mature team has a metric like "5xx rate > 0.5% over 5 minutes" that pages oncall. Why not alert on absolute count? Because traffic varies — 100 errors in a quiet period is catastrophic, 100 errors at peak is noise. Rate (errors / total) is the stable signal. Why a window? Because transient spikes are common (one bad deploy, one transient dependency hiccup). Five-minute windows balance responsiveness with noise rejection.

The 4xx nuances that matter in production:
  • 401 vs 403: a sudden jump in 401s often means an auth service is failing or keys expired. 403s mean "I authenticated you but something is denied" — could be a permissions bug or an attempted privilege escalation. Dashboards should split these.
  • 404: scraped by search engines, broken links, or probing. A baseline level of 404s is healthy; a jump usually means a deploy broke routing.
  • 429 Too Many Requests: rate-limit hits. A well-behaved client should back off. If you see sustained 429s for legitimate users, your limits are too tight; if you see 429s for one specific client, they're misbehaving. Include Retry-After so clients know when to retry.
  • 499 (nginx-specific): client closed the connection before we responded. Often means your backend is too slow; the client gave up waiting. Not an HTTP standard code but very useful operationally.
The 5xx distinctions in a load-balanced system:
  • 500 Internal Server Error: uncaught exception in your app. Stack trace hopefully went somewhere.
  • 502 Bad Gateway: the LB got a garbage response from the backend. Typical causes: backend crashed mid-request, backend closed the connection unexpectedly, protocol mismatch. Root-cause inside the backend.
  • 503 Service Unavailable: no healthy backends (all health checks failing), or the LB itself is throttling (e.g., CloudFront under extreme load). "My service is down entirely".
  • 504 Gateway Timeout: backend didn't respond in time. The LB has a request timeout (often 30-60s); if the backend doesn't write the response within that, the LB cuts the connection and returns 504. Could be slow DB queries, deadlocks, or just a legitimately long operation.
Idempotency + retries — the interview test. Given a 5xx response, can you safely retry? Depends on the verb and the design:
  • GET, HEAD, PUT, DELETE are idempotent by HTTP spec — repeating them should produce the same outcome. Safe to retry.
  • POST is not idempotent. A 500 on POST /charge might mean "we charged you and the response was lost" or "we failed before charging". Retrying could double-charge. Idempotency keys (client-generated UUID sent in a header; server dedupes) are the standard solution.
  • A 429 response with Retry-After is explicit permission to retry after that delay — respect it.
Dashboards that tell a story:
  • Status code histogram over time — a stacked chart of 2xx/3xx/4xx/5xx rates. The shape tells you what's changing.
  • 5xx rate per endpoint — errors aren't usually uniform; one broken endpoint stands out.
  • P50, P95, P99 latency alongside status codes — many outages start as latency problems (5xx is a late signal).
  • Status code distribution per caller (identified by API key or client IP) — detects "this one integration partner's traffic is failing".

🔍 DEEP DIVE — THREE ROLES, OFTEN BLURRED

The distinction between "web server", "application server", and "reverse proxy" has blurred as software has evolved. The roles are still distinct; it's just that modern tools often play more than one.

Web server (the classical role): terminate HTTP connections from clients, serve static files (HTML, CSS, JS, images), and handle protocol-level concerns (keepalives, HTTP/2 multiplexing, request parsing). Apache and nginx were born as web servers. Serving a static site doesn't need anything more — bytes on disk flow to bytes on wire with minimal processing. Performance is I/O-bound and scales per connection; an event-driven server (nginx) can handle 100k concurrent connections on modest hardware.

Application server (the execution role): run your application code — Python, Java, Ruby, Go — to generate dynamic responses. Gunicorn, uWSGI (Python), Tomcat, Jetty (Java), Puma (Ruby) are all app servers. They speak either HTTP directly or a private protocol (WSGI, FastCGI, AJP) to a web server in front. App servers are CPU-bound and typically much lower per-process concurrency — a Python/Gunicorn worker handles one request at a time (with some async improvements); you run many workers to scale.

Reverse proxy (the routing role): sits between clients and one or more backends; clients see one address, the proxy decides which backend gets the request. Functions: load balancing, TLS termination, caching, rate limiting, request rewriting, header manipulation, authentication at the edge, WebSocket proxying. Nginx, Envoy, HAProxy, Traefik are the popular choices. ALB and CloudFront are AWS-managed versions.

Why "web server" and "reverse proxy" blur: nginx can be either (or both at once). A single nginx instance might serve /static/* from disk directly (web server role), proxy /api/* to a Gunicorn upstream (reverse proxy role), and route /admin/* to a different backend. The config file specifies the behavior per location.

The canonical production topology: 
Client

Each layer adds value: CDN reduces latency and origin load; cloud LB provides auto-scaling and health-checked entry; reverse proxy adds fine-grained control the cloud LB lacks; app server runs code; DB/cache store state. Simpler apps skip layers — a small service might just be ALB → Gunicorn, no nginx needed; a static site is just CloudFront → S3, no compute at all.

Why a reverse proxy in front of an app server — even when the app server speaks HTTP natively?
  • Slow clients: the reverse proxy buffers. A mobile user on a bad connection takes 10 seconds to send a 1MB upload; you don't want your app-server worker tied up reading bytes that slowly. The proxy accepts the full request first, then hands it to the app server in one burst.
  • Static file serving: handing /images/logo.png back from disk is millions of times faster in nginx than in Python code.
  • TLS termination: Python/Java crypto is slower than nginx's, and cert management in one place is cleaner.
  • Operational safety: nginx can return a cached page or a maintenance message when the backend is down, instead of a TCP error.
  • Security: rate limiting, WAF rules, header stripping happen at the edge.
  • Zero-downtime deploys: nginx can drain connections from the old backend while routing new ones to the new backend.
The modern wrinkle: Go and similar languages. A native-compiled, event-loop-based service (Go, Rust, Node) can handle tens of thousands of concurrent connections directly — the "slow clients" argument weakens. Many Go services deploy as just the binary behind an ALB, no nginx in the middle. That's fine; add a reverse proxy when you need a feature it provides, not as cargo-cult architecture.

Event-driven vs thread-per-request is the key architectural difference that explains why some servers scale and others don't:
  • Thread/process-per-request (Apache prefork, classic Java servlets): one OS thread per concurrent request. Memory grows linearly with concurrency; thread context switches are expensive. Caps out around a few thousand concurrent connections.
  • Event-driven (nginx, Node, Go, Python async): one (or a few) threads using epoll/kqueue to handle thousands of connections cooperatively. Memory per connection is bytes, not MB. Caps at 100k+ connections, but CPU-bound work blocks the loop — you need to be careful about what runs in the event thread.

🔍 DEEP DIVE — AMAZON-FLAVORED VARIANT

The interviewer may be looking for details about CloudFront, Route 53, ALBs, and large-scale architecture specifically. DNS: Route 53 with latency-based routing. amazon.com has multiple A records for different regions. Route 53 checks your client's IP against EDNS Client Subnet and returns the region with the lowest latency. So a user in Frankfurt gets a different IP than one in Tokyo, even though the DNS name is identical. CNAME chains: www.amazon.com might CNAME to a CloudFront distribution, which in turn has anycast IPs announced from hundreds of edge POPs globally.

CDN: CloudFront edge. The first TCP connection goes to the closest CloudFront POP (Point of Presence — a data center physically close to the user). CloudFront terminates TLS there. If the request is for a cacheable static asset (product images, CSS, JS), CloudFront serves it directly without touching origin. For dynamic content (/, /cart), CloudFront forwards to the origin over a backbone-optimized connection (AWS's private fiber), which is much faster than the public internet. POP-to-origin latency is often 5-20ms even across continents.

The origin layer. CloudFront connects to an ALB in the region. ALB does health-checked load balancing to backend fleets, typically hundreds of EC2 instances or ECS tasks across multiple availability zones. Each fleet runs behind an auto-scaling group that adds/removes capacity based on traffic.

The request inside Amazon. The ALB's selected backend receives the request. Amazon's architecture is famously services-all-the-way-down — a single GET / for the homepage fans out into hundreds of internal service calls (product catalog, personalization, recommendations, inventory, price, ratings, shipping eligibility, cart, user session, A/B test assignment). Each is its own service, each has its own fleet, each has its own SLA. Failures are isolated — if the recommendations service is down, the page still renders (with a fallback), not 500s.

Caching layers everywhere. Before a request hits a database, it probably passes through multiple caches: ElastiCache (Redis/Memcached), in-process caches, DynamoDB Accelerator (DAX). Many reads never touch the primary datastore.

Response path. Assembled response goes back through ALB → CloudFront edge (may cache if headers permit) → TLS encrypted → user. Client-side rendering continues: progressive HTML parse, sub-resource fetches (many are already warm in CloudFront), JavaScript hydration, image lazy loading. Amazon is aggressive about the critical rendering path — inline critical CSS, defer non-critical JS, preload key images — because a faster page = more sales.

Observability in this flow. Every request has a trace ID (X-Amzn-Trace-Id header) that follows it through every service. When something is slow, you pull up the trace and see "40ms in DNS, 5ms TLS, 12ms at the ALB, 180ms at the recommendations service with a 200ms timeout" — the slow service is named immediately. This is AWS X-Ray / CloudWatch ServiceLens / internal tools territory.

Failure modes an interviewer might ask about:
  • "A whole region is down." Route 53 health checks detect this; the DNS answer switches to another region. Uses failover routing policy. Client sees a ~TTL-worth of disruption.
  • "CloudFront edge POP is down." Anycast routing automatically shifts clients to the next-closest POP. Invisible to users.
  • "Certificate expiry." CloudFront uses ACM (AWS Certificate Manager) which auto-renews; the cert is distributed to every POP. Manual cert management is a common source of outages elsewhere.
  • "DDoS on a single IP." CloudFront + AWS Shield absorb the attack at the edge before it reaches the origin. Shield Advanced adds WAF rules.
The Amazon differentiator in this answer: talk about trace IDs, fallback behavior for slow dependencies, and regional failover. Those three show you think at operational scale, not just about a single request.

🔍 DEEP DIVE — PUBLIC-KEY CRYPTO IN ONE PROTOCOL

SSH key authentication replaces "what you know" (password) with "what you have" (private key). The private key never leaves your machine — not over the wire, not to the server. The server only has your public key and uses it to verify that you possess the matching private key. This is fundamentally stronger than passwords because (a) keys aren't phishable, (b) they can be much higher entropy than any password, (c) a compromised server learns your public key but can't impersonate you elsewhere.

How the authentication actually flows:
  1. Client connects, TCP established, SSH protocol version negotiated, key exchange (Diffie-Hellman variant) establishes a shared symmetric key — all further traffic is encrypted regardless of auth method.
  2. Client declares "I want to authenticate as ramya using public-key auth" and offers its public key fingerprint.
  3. Server checks ~ramya/.ssh/authorized_keys; if it contains the offered public key, it generates a random challenge and sends it encrypted for that public key.
  4. Only the matching private key can decrypt it (or more precisely, sign it — the details depend on key type). Client signs the challenge + session identifier with its private key and sends back.
  5. Server verifies the signature using the public key; if it matches, authentication succeeds. The private key never crosses the network; only signatures do.
Key types and their tradeoffs:
  • RSA-2048 / RSA-4096: the historical default. Still safe; RSA-4096 is overkill for most cases. Some very old servers only support RSA.
  • Ed25519: the modern recommendation. Much smaller keys (~68 bytes public), faster signing/verification, resistant to side-channel attacks, designed specifically for the "one-shot signature" use case SSH needs. Use Ed25519 unless you must support an ancient server.
  • ECDSA (P-256): middle ground — smaller and faster than RSA, but with some caveats about nonce reuse that Ed25519 avoids.
  • DSA: deprecated, don't use.
The permissions matter. SSH is paranoid about key file modes because a world-readable private key is a serious vulnerability. SSH will refuse to load keys if:
  • ~/.ssh is group- or world-writable (must be 700).
  • ~/.ssh/id_* (private keys) are readable by anyone else (must be 600).
  • The user's home directory itself is too permissive.
The server's auth.log will log Authentication refused: bad ownership or modes — that's your signal.

ssh-agent is the convenience/security tradeoff. Without an agent, you'd type your key's passphrase on every SSH command. The agent holds your unlocked private keys in memory and signs on demand. Start it (usually automatic on login), add keys with ssh-add. Always use a passphrase on your private key — otherwise a stolen laptop = full access everywhere. On macOS, ssh-add --apple-use-keychain ~/.ssh/id_ed25519 stores the passphrase in Keychain so you're prompted once per reboot.

Hardening sshd_config on the server side:
  • PasswordAuthentication no — disable passwords entirely once keys work. Stops brute-force attacks cold.
  • PermitRootLogin prohibit-password (or better, no) — never allow root login with a password; with keys, only if essential.
  • PubkeyAuthentication yes, ChallengeResponseAuthentication no.
  • AllowUsers ramya ops-admin — whitelist specific users rather than implicitly allowing all.
  • MaxAuthTries 3, LoginGraceTime 30 — bound brute-force attempts.
  • AllowAgentForwarding no unless explicitly needed — prefer ProxyJump.
  • PermitEmptyPasswords no, X11Forwarding no by default.
SSH certificates — the enterprise-scale evolution. Manually managing authorized_keys across thousands of hosts is a nightmare (onboarding, offboarding, rotation). SSH CA: a trusted signing authority issues short-lived certificates (1-24 hour validity) that include your identity and permitted principals. Servers are configured with TrustedUserCAKeys /etc/ssh/ca.pub and accept any certificate signed by the CA. Revocation is implicit — expired certs stop working. Tools: HashiCorp Vault SSH, AWS IAM + EC2 Instance Connect, Teleport, BastionZero. This is the AFT-scale pattern; raw authorized_keys is for small shops.

What an attacker can still do if they have your private key: everything you can. Mitigations:
  • Passphrase on the key — slows them down (needs local access + passphrase).
  • Hardware-backed keys (YubiKey, Touch ID in macOS, TPM) — the private key never leaves the device. Signing requires physical presence.
  • Short-lived certificates — compromised material expires before it can be used much.
  • Separate keys per environment — dev key compromise doesn't leak prod.

🔍 DEEP DIVE — TLS GIVES YOU THREE PROPERTIES

TLS is the thing that turns HTTP into HTTPS, SMTP into SMTPS, and raw TCP into a private channel. Its job is to deliver three security properties over an untrusted network:
  1. Confidentiality — nobody in between can read the data.
  2. Integrity — nobody in between can modify the data without detection.
  3. Authentication — the client can verify the server is who it claims to be (and optionally the reverse).
The handshake establishes all three before any application data flows.

Why the handshake mixes asymmetric and symmetric crypto. Asymmetric crypto (RSA, ECDSA) is slow — milliseconds per operation, not useful for streaming a file. Symmetric crypto (AES, ChaCha20) is fast — gigabits per second. So TLS uses asymmetric only once, at the start, to agree on a shared symmetric key, then encrypts everything after that symmetrically. The handshake is really just a key exchange, plus identity verification via certificates.

TLS 1.2 handshake (the version most questions describe):
  • ClientHello: client sends the list of cipher suites it supports, TLS version, a random number, SNI (the hostname it wants to talk to — essential for virtual hosting), ALPN (protocols it speaks: HTTP/1.1, h2, h3), and TLS extensions.
  • ServerHello: server picks one cipher suite from the offered list (preferring something like TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384), sends its own random, and follows with: Certificate (the full chain, leaf + intermediates), ServerKeyExchange (ECDHE parameters — ephemeral public key for the Diffie-Hellman exchange, signed with the server's long-term key from the cert), and ServerHelloDone.
  • Client verifies the certificate. Walks the chain from leaf to root, checking each signature. Root must be in the client's trust store. Verifies the leaf's SAN/CN matches the hostname. Checks expiry, revocation (OCSP or CRL).
  • ClientKeyExchange: client sends its ECDHE public key. Now both sides have each other's ECDHE public keys and can compute the shared secret without ever transmitting it.
  • Key derivation: both sides derive session keys from (client random + server random + shared secret) using a key derivation function.
  • ChangeCipherSpec + Finished: both sides confirm they're switching to the encrypted channel. The Finished message includes a hash of the entire handshake, proving both parties saw the same sequence — prevents downgrade attacks.
That's two round trips before the application can send its first byte — noticeable on high-latency links.

TLS 1.3 — the modern version. TLS 1.3 (2018) cut the fat: removed obsolete ciphers, mandated forward secrecy, merged several round trips. The handshake is one round trip, and for resumed sessions (client has a ticket from a previous connection), it can be zero round trips — encrypted application data in the very first packet. This matters enormously for mobile and global apps where RTT dominates.

Perfect Forward Secrecy (PFS) via ECDHE. In older "RSA key exchange" mode, the client encrypted the session key with the server's public key. If the server's private key ever leaked, every past recorded session could be decrypted retroactively. ECDHE uses ephemeral keys (generated per-session, thrown away after) — even if the server's long-term key is stolen later, past sessions stay private. TLS 1.3 mandates PFS; TLS 1.2 ECDHE cipher suites provide it.

Certificate verification is where most breakage happens. Common failure modes:
  • Expired certificate. Certs have a notAfter date. Expired = all clients refuse. Let's Encrypt autorenews; AWS ACM autorenews. Self-managed certs need monitoring (cert-manager in Kubernetes, or a simple cron with openssl x509 -enddate).
  • Hostname mismatch. Cert says www.example.com, user connects to example.com. Fix: issue a cert with both as SANs, or use a wildcard *.example.com.
  • Untrusted CA / missing intermediate. The server must send the full chain (leaf + intermediates, but not root; root is in the client's trust store). If only the leaf is served, clients that don't happen to have the intermediate cached will fail. Test with openssl s_client -connect host:443 -servername host and look for "Verify return code: 21 (unable to verify the first certificate)".
  • Clock skew. If the client's clock is wildly off, the cert will appear either not-yet-valid or expired. NTP matters.
  • Revocation. Certs can be revoked before expiry. Historically via CRLs (download a big list periodically), now usually OCSP (ask "is this cert revoked?" per connection). OCSP Stapling lets the server cache and serve the OCSP response, eliminating client-side OCSP round trips.
The operational tools:
  • openssl s_client -connect host:443 -servername host -showcerts — shows the full chain the server is presenting, cipher negotiated, everything.
  • openssl x509 -in cert.pem -text -noout — decodes a cert file into readable fields.
  • echo | openssl s_client -connect host:443 2>/dev/null | openssl x509 -noout -dates — quick expiry check.
  • sslscan host, testssl.sh host — automated audit tools; show which protocols and ciphers a server supports, flag weaknesses.
  • curl -v https://host — shows the client-side view including SNI, ALPN, and verification result.
The AFT-flavor follow-up: "At Amazon scale, how do you manage certs?" Answer: ACM (AWS Certificate Manager) for public certs on AWS resources (auto-renewed, integrated with ALB/CloudFront/API Gateway); ACM Private CA for internal TLS. HashiCorp Vault PKI or cert-manager + Let's Encrypt for Kubernetes. Short-lived certs (hours not years) are the direction of travel — no revocation drama, automated rotation.

🔍 DEEP DIVE — THE THREAT MODEL OF ENV VARS

Env vars are fine for configuration, dangerous for secrets. The 12-factor-app mantra "config via environment" conflates non-sensitive config (log level, port number, feature flag) with sensitive secrets (API keys, DB passwords). They need different handling. This question is really "do you know where env vars leak?"

The six leak paths — memorize these:
  1. /proc/<pid>/environ. Any process on the system that shares your UID can cat this and see every env var attached to your process — cat /proc/$(pgrep myapp)/environ | tr '\0' '\n'. Root can always read it. On a shared host or container with insufficient isolation, this is a real leak.
  2. ps eww PID. On some systems / configurations, the full environment shows up in process listings. Less common on modern Linux (requires the same UID, and most distros have toned this down), but still possible.
  3. Command-line arguments — worse than env. mysql -u root -pHUNTER2 is visible to anyone on the host via ps aux. At least env vars require the same UID. Never pass secrets on the command line.
  4. Child process inheritance. Any process you spawn inherits your entire env. Run npm install while AWS_SECRET_ACCESS_KEY is set, and every post-install script in every dependency has access to your creds. Be surgical — set secrets right before the call that needs them, unset after, or pass them via stdin or a short-lived file.
  5. Core dumps / crash reports. When a process crashes, the kernel may write a core file containing the full memory state — including env vars. Crash reporting services (Sentry, Crashlytics) may exfiltrate this to their servers. Disable core dumps (ulimit -c 0) in production or scrub reports.
  6. Logs. Frameworks often log the environment on startup for debugging. Error tracking may capture request context including env. Log scrubbing is needed; better, never put secrets in env in the first place.
Why secrets managers are the right answer at AFT scale:
  • AWS Secrets Manager and SSM Parameter Store (SecureString): secrets stored encrypted at rest (KMS), accessed via IAM, with CloudTrail audit logs. Your application fetches at startup (or per-use) using its instance/role credentials — no long-lived secret lives on disk anywhere. Automatic rotation is supported (Secrets Manager can rotate DB passwords on schedule, coordinating with the DB to update both places).
  • HashiCorp Vault: cloud-agnostic version. Same pattern: app authenticates to Vault (via AWS IAM, Kubernetes service account, short-lived tokens), fetches secrets, uses them without writing to disk. Supports dynamic secrets (Vault creates a fresh DB user for each app boot, revokes when the lease expires).
  • Kubernetes Secrets + sealed-secrets / SOPS: K8s Secrets are base64-encoded-not-encrypted in etcd by default; enable encryption at rest. For GitOps (secrets in Git), SOPS encrypts values with KMS/PGP before commit, decrypts at deploy. Sealed Secrets (Bitnami) encrypts with a controller-managed key; only the cluster can decrypt, so you can safely push to a public repo.
The acceptable middle ground: if you must use env vars (legacy apps, constrained environments, quick prototypes), at least do these:
  • Never commit .env files. .gitignore them. git-secrets / trufflehog / gitleaks scan commits for accidental secret leaks.
  • Use systemd's EnvironmentFile=/etc/myapp/secret.env with the file owned by root and mode 600. Systemd reads it, spawns the service with the env set, and the file is never world-readable.
  • Separate secrets from config. Commit config.env.example with placeholders; the real secret.env lives only on the server.
  • Rotate on any suspicion of leak. Have a runbook: "credentials N leaked — here are the steps to rotate and validate".
  • Use short-lived credentials where possible — AWS IAM roles instead of access keys, Vault dynamic secrets, database auth via IAM/Kerberos instead of passwords.
The zero-trust direction: modern architecture moves toward no secrets at all in environment or config.
  • IAM roles for EC2/ECS/Lambda: the instance metadata service (169.254.169.254) returns short-lived credentials. No access key to leak because there isn't one.
  • OIDC for CI/CD: GitHub Actions, GitLab CI use OIDC to authenticate to AWS/GCP without static tokens — every pipeline run gets fresh, time-bounded credentials.
  • mTLS for service-to-service: each service has a short-lived cert issued by the mesh (Istio, Linkerd, App Mesh). No bearer tokens to steal.
  • Database IAM auth: RDS can authenticate via IAM tokens (15-minute lifetime), no DB password exists.
The one rule to emphasize in the interview: secrets should never be in your shell history, your Git log, your CI config, or your container image. If any of those happens, rotate immediately and investigate how. GitHub's secret scanning is good; trufflehog or gitleaks on PR is better.
