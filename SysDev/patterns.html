🔍 What's Intentionally Not Here (AFT L4 scope)

Some "canonical" interview patterns are deliberately excluded. For an L4 AFT Support SDE role, the interview weight is on production instincts, Linux/ops fluency, and clean OOP, not competitive-programming depth. If you see these in other prep lists, don't panic — here's how to think about each.

Pattern Why skip for AFT L4 If it does come up…
Dynamic Programming
(knapsack, LIS, edit distance)		 L4 SysDev interviews favor pragmatic code over tricky recurrences. AFT scenarios are operational. Recognize the signal ("overlapping subproblems" or "count the number of ways"), state the recurrence, and say out loud: "I'd memoize with @functools.lru_cache or build a bottom-up table." Knowing climbing stairs / coin change is enough to survive.
Backtracking
(N-queens, permutations)		 Rare for L4. Most "all permutations" questions resolve into DFS, which is covered (P7). It's just DFS with "try, recurse, undo". Template: choose → recurse → unchoose. Pruning (reject early) is the only real trick.
Union-Find (DSU) High-signal for graph specialists; low-signal for AFT. BFS/DFS handle most connectivity questions. Two ops: find(x) with path compression, union(a,b) by rank. Use case: "are these two things connected?" on streaming edges. If asked, explain the concept and fall back to BFS.
Dijkstra / Weighted graphs More relevant for routing or infra engineers. AFT graph questions usually have unit weights → BFS suffices. "BFS but with a min-heap instead of a queue, relaxing edges." Python: heapq + dist dict. Say out loud: "I'd use Dijkstra; it's priority-queue BFS for weighted edges."
Segment Tree / BIT (Fenwick) Competitive-programming territory. You will almost certainly never see this at L4 AFT. Safe to punt. If pressed on "range sum with updates", mention segment tree (O(log n)) as the name and explain you'd look up the exact implementation.
Trie Niche for AFT. But cheap to learn and shows up in autocomplete / log-filter questions. A tree of character-keyed dicts. Insert/search in O(word length). Worth 10 minutes of review if you have time — otherwise deprioritize.
Bit manipulation Python hides bits behind integers. Rare signal for systems/ops roles. Know x & (x-1) clears the lowest set bit, XOR finds the unpaired number, bin(x).count('1') counts set bits. That covers 90% of the questions you'd see.
SQL / Database queries Explicitly skipped per your constraint. AFT interviews rarely live-code SQL; if they do, express the logic in Python/pandas. If asked, redirect: "I'd approach this with Python — group-by and count using collections.Counter or a pandas groupby." That demonstrates the thinking; syntax is tool-specific.

⚠ Rule of thumb: If it's not in the 14 above, and an interviewer asks it, you're allowed to say "I'm less practiced on that — can I sketch the idea and fall back to a simpler approach that also solves it?" That's a senior move, not a weakness.


1. Two Pointers   O(n)

Signals: "sorted array", "pair with target", "two numbers sum to"

💡 WHY IT WORKS A sorted array carries an ordering invariant: if a[l] + a[r] is too small, no pair involving a[l] with anything smaller can reach the target — so l can advance. Each move eliminates an entire row or column of the implicit n×n pair grid, collapsing the O(n²) search to O(n). It's a directed squeeze, not a search.
📝 MENTAL MODEL "Sorted + pair = squeeze from both ends; each step kills a row or column."
⚠ TRAP Duplicate pairs. On a sorted array with duplicates, after finding a pair you must skip past all equal neighbors on both sides (while l < r and a[l] == a[l+1]: l += 1) — otherwise 3Sum and similar return the same triplet many times. Also: applying two-pointers to an unsorted array silently gives wrong answers.
🔶 ESCALATION Two pointers → fix one pointer, two-pointer the rest (3Sum) → two pointers + sliding window hybrid (container with most water) → binary search on one side (closest pair sum across two arrays). When array isn't sortable in-place, reach for a hash map instead.
🎯 REAL QUESTION "Given a sorted array and a target, return all unique pairs that sum to the target."
  • l = 0, r = n-1; compare a[l]+a[r] to target.
  • If equal, record, then advance both and skip duplicates on each side.
  • If too small, l++; too big, r--.
  • Explicitly call out duplicate skipping — that's what separates Meets-Bar from Raises-Bar.
🔗 BRIDGES Cousin of binary search (both exploit sortedness). Often combined with hash map when the array is unsorted and can't be sorted. The "while" logic inside a sliding window IS two-pointer thinking, just with different invariants.
🐍 PYTHON + PRACTICE Stdlib: plain integer indices; bisect.bisect_left if you need to find the other pointer in O(log n); sorted() to get into two-pointer shape.
Practice: see Coding § Data Structures for the two-pointer mindset applied to Min Stack (Q15). For 3Sum-style drill, try any LeetCode "2Sum II" or "Container With Most Water".
📝 PRACTICE PROBLEMS
1. Two Sum in Sorted Array
"Given sorted array, find two numbers that sum to target."		Canonical — squeeze from both ends. Skip duplicates on both sides to avoid repeat pairs.
2. Container With Most Water
"Heights on x-axis, find two that hold the most water."		The twist: always move the shorter pointer — any pair with the taller one as the max is already suboptimal.
3. Remove Duplicates from Sorted Array (in-place)
"Return length of deduped array, modify in place."		Read pointer advances through all; write pointer only advances on new values. Classic "in-place" two-pointer.
4. 3Sum (find all triplets summing to zero)
"Return all unique triplets that sum to 0."		Escalation — fix one pointer, two-pointer the other two. Duplicate-skipping is the tricky part.
5. Merge Two Sorted Arrays
"Merge B into A (A has enough space) in-place."		Twist: fill from the back, not the front, so you never overwrite values you still need.
6. Valid Palindrome (with alphanum filter)
"Is this string a palindrome, ignoring non-alphanumeric?"		Two pointers from both ends; skip invalid chars, compare case-insensitively. Shows two-pointer on strings, not just numbers.


2. Sliding Window   O(n)

Signals: "longest/shortest substring", "window of size k", "contains at most k distinct"

💡 WHY IT WORKS A sliding window turns "examine every subarray" (O(n²)) into "extend the right edge, shrink from the left when the invariant breaks" (O(n)). The key is that each element is added once and removed at most once — so total work is amortized linear even though the inner while-loop looks nested.
📝 MENTAL MODEL "Expand right, shrink left when the window becomes invalid. Each element enters and leaves at most once."
⚠ TRAP Confusing fixed-size with variable-size. Fixed window (size = k) always shrinks when right advances. Variable window shrinks only when invariant breaks. Mixing the two gives off-by-one bugs. Also: updating the answer at the wrong moment — do it after the window becomes valid, not during shrinking.
🔶 ESCALATION Basic counter in window → hash map in window (at-most-k distinct chars) → monotonic deque in window (sliding window max/min) → two hash maps / frequency diff (minimum window substring). For the k-th largest in a window, upgrade to a heap or a multiset/sorted container.
🎯 REAL QUESTION "Longest substring without repeating characters."
  • Expand right; keep a dict last_seen[ch] = index.
  • If s[right] is in dict and last_seen[ch] ≥ left, jump left = last_seen[ch] + 1.
  • Update last_seen[s[right]] = right.
  • Track max_len = max(max_len, right - left + 1) each iteration. O(n).
🔗 BRIDGES Sliding windows almost always use a hash map or Counter internally to track contents. For "sliding window max", you reach for a monotonic deque (cousin of monotonic stack). Fundamentally: sliding window = two-pointer with an invariant on the contents.
🐍 PYTHON + PRACTICE Stdlib: collections.Counter or defaultdict(int) for window contents; collections.deque for O(1) append/popleft and for monotonic deque (window max/min).
Practice: see Coding Q10 · Rate Limiter (sliding-window limiter is literally this pattern). Drill: "longest substring with at most K distinct" → shrink-when-invalid template.
📝 PRACTICE PROBLEMS
1. Max Sum Subarray of Size K (fixed window)
"Find max sum of any contiguous subarray of exactly K elements."		Fixed-size window — the simplest variant. Slide the window, update sum by adding new + subtracting old. O(n).
2. Longest Substring Without Repeating Characters
"Find the longest substring with all unique characters."		Variable-size + hash map. Expand right until duplicate; then shrink left until unique again. Map tracks last-seen index.
3. Minimum Window Substring
"Smallest window in S containing all chars of T."		The hardest sliding-window interview question. Expand until valid, then shrink while still valid. Two Counters: one for T, one for current window.
4. Longest Substring with At Most K Distinct Characters
"Find longest window with ≤ K different characters."		Shrink-when-invalid template. When len(map) > K, shrink until back to K.
5. Sliding Window Maximum
"For each window of size K, return the max."		Escalation — needs a monotonic deque, not just a Counter. The deque holds indices of candidates; pop smaller ones on the right when adding a bigger one. O(n) total.
6. Sliding-Window Rate Limiter
"Allow N requests per user per minute."		Production pattern: keep a deque of timestamps; on each request, drop timestamps older than 60s, check len(deque) < N. Exact same shape, operational context. See Coding Q10.


3. Prefix Sum + Hashmap   O(n)

Signals: "subarray sum equals k", "count subarrays", "range sum queries"

💡 WHY IT WORKS Any subarray sum sum(i..j) equals prefix[j] - prefix[i-1]. So asking "does a subarray sum to k?" becomes "does prefix[j] - k appear earlier in the prefix array?" — a classic reduce-to-two-sum trick solvable with a hash map in O(n). The insight: pair queries become lookups.
📝 MENTAL MODEL "Subarray sums = prefix differences. Count them with a hash map."
⚠ TRAP Forgetting to seed seen = {0: 1}. Without this sentinel, you miss subarrays that start at index 0 — their prefix equals k, so prefix - k = 0, which must be "seen" once. Second trap: applying prefix-sum with negative numbers but a sliding window (sliding window needs monotonicity of sums as you shrink; negatives break it).
🔶 ESCALATION 1D prefix sum → 2D prefix sum for matrix range-sum queries → difference array for range updates in O(1) → Fenwick tree / segment tree for mutable prefix sums with log n updates. For "subarray sum divisible by k", swap the key to prefix % k.
🎯 REAL QUESTION "Count the number of contiguous subarrays whose sum equals k."
  • Maintain running prefix and seen = {0: 1}.
  • For each element, add to prefix; answer += seen.get(prefix - k, 0).
  • Then seen[prefix] += 1.
  • Works with negatives; sliding window would not.
🔗 BRIDGES Prefix sum is reduce-to-two-sum — it depends on hash map. For positive-only arrays with "sum ≤ k" shape, a sliding window often works instead. For updates + queries, step up to Fenwick/segment tree (think of it as a "prefix sum with logs").
🐍 PYTHON + PRACTICE Stdlib: itertools.accumulate builds the prefix array in one line (list(accumulate(nums))); collections.defaultdict(int) for the frequency map of prefix sums.
Practice: not directly covered in coding.html (we focus on ops-heavy questions) — drill LeetCode "Subarray Sum Equals K" and "Continuous Subarray Sum". The pattern generalizes to 2D (image integral / matrix region sums).
📝 PRACTICE PROBLEMS
1. Range Sum Query (immutable)
"Given array, answer many queries of form sum(nums[i..j])."		Build prefix array once in O(n). Each query is prefix[j+1] - prefix[i] — O(1). Canonical use case.
2. Subarray Sum Equals K
"Count contiguous subarrays summing to K."		Prefix sum + hash map. Count how many times (current_prefix - K) appeared. Works with negatives — sliding window would fail.
3. Continuous Subarray Sum (multiple of K)
"Is there a subarray whose sum is a multiple of K?"		Twist: store prefix % K in the map, not the prefix itself. Two prefixes with the same mod = subarray sum divisible by K.
4. Product of Array Except Self
"For each index, return product of all other elements (no division)."		Prefix + suffix variant: two passes, one accumulating products left-to-right, one right-to-left. Same mental model as prefix sum.
5. 2D Range Sum / Image Integral
"Given matrix, answer many sum queries for sub-rectangles."		Escalation to 2D: build integral image with inclusion-exclusion: I[r][c] = m[r][c] + I[r-1][c] + I[r][c-1] - I[r-1][c-1]. Rectangle sum is O(1) after.
6. Find Pivot Index
"Index where sum of left == sum of right."		Single-pass with running prefix: at each i, check prefix[i] == total - prefix[i] - nums[i]. Good warm-up.


4. Hash Map / Counter   O(n)

Signals: "first unique", "two sum", "count occurrences", "dedupe", "anagram"

💡 WHY IT WORKS Hash maps turn "have I seen this before?" and "how many times?" from O(n) scans into O(1) lookups by trading space for time. They break the O(n²) barrier for pair-lookup problems by letting each element do a constant-time query for its partner. If brute force is O(n²), first instinct should be: "what if I hash something?"
📝 MENTAL MODEL "Trade O(n) space for O(n) time. If brute force is O(n²) with nested loops, you almost always want a hash map."
⚠ TRAP Hashable keys. Lists aren't hashable in Python — use tuple. For character frequency keys, forgetting that Counter equality is order-independent saves you. Second trap: ordering. Python's dict preserves insertion order (3.7+) but don't rely on it for correctness; if order matters, say so explicitly.
🔶 ESCALATION Plain dict → Counter (.most_common(k), subtraction, +) → defaultdict (auto-init for grouping) → two hash maps (frequency diff, anagram groups, bidirectional) → hash map + linked list (LRU, ordered dict). For top-K counts, combine Counter with a heap.
🎯 REAL QUESTION "Return indices of two numbers in an array that sum to target."
  • Single pass: for each num, check if target - num is in seen.
  • If yes, return [seen[target-num], i].
  • Else seen[num] = i.
  • Key detail: store the complement's index, not the complement — because you need to return both indices.
🔗 BRIDGES The universal "O(n²) → O(n)" upgrade. Underlies prefix-sum (lookup complement), sliding window (track contents), LRU (key→node), top-K (counts feed a heap), and dedup for graph visited sets. If you're asked a problem and don't see the pattern, ask yourself: "What would I want to look up in O(1)?"
🐍 PYTHON + PRACTICE Stdlib: collections.Counter (frequency in one line); collections.defaultdict (auto-init); dict.setdefault when you can't use defaultdict; set() for O(1) membership.
Practice: Coding Q1 · Anagram (Counter-based O(n) beats sort-based O(n log n)) and Q9 · Most Repeated Phone Number (Counter + most_common).
📝 PRACTICE PROBLEMS
1. Two Sum (unsorted)
"Return indices of two numbers that sum to target."		Canonical. One pass: for each num, check if target - num is in the map; else add current. O(n) time, O(n) space — beats sorting.
2. Valid Anagram
"Are two strings anagrams?"		Build Counter for both, compare. Or: one Counter; increment for string A, decrement for string B; all values must be 0. See Coding Q1.
3. Group Anagrams
"Group words that are anagrams of each other."		Key design: sorted chars OR char-count tuple as the dict key. All anagrams map to the same key.
4. First Unique Character in a String
"Find the first non-repeating character."		Counter first pass; second pass find first char with count 1. Two passes are fine and often clearer than one.
5. Contains Duplicate / Within K Distance
"Is there a duplicate within K indices?"		Hash map of value → last_seen_index. On collision, check i - last <= K. Combines hash with a distance constraint.
6. Happy Number
"Repeatedly square+sum digits; does it reach 1?"		Hash set for cycle detection — if we see the same intermediate twice, it's a cycle (and not 1). Same set-based cycle idea appears in graph-traversal.


5. Stack (incl. Monotonic)   O(n)

Signals: "matching brackets", "next greater/smaller", "largest rectangle", "parse expression"

💡 WHY IT WORKS Stack's LIFO property mirrors nested structure — the most recent opener must match the next closer. For monotonic stacks, the insight is subtler: once an element is "dominated" by a newer one (e.g., bigger rating appears), it can never be the answer for anything further right — so pop it. Each element is pushed and popped at most once, giving amortized O(n).
📝 MENTAL MODEL "Nesting or 'next bigger/smaller' → stack. Each element joins and leaves at most once."
⚠ TRAP Counter instead of stack for bracket matching. "Just count opens and closes" gives wrong answer for ([)]. For monotonic stacks, forgetting to process leftover elements at the end (which had no next-greater) is the common bug. Also: indexing vs values — decide upfront which you store.
🔶 ESCALATION Plain stack → monotonic stack (increasing/decreasing invariant) → monotonic deque (sliding window max/min needs pop from both ends) → two stacks (min-stack, queue from stacks). For expression evaluation, upgrade to Shunting-yard or operator-precedence parsing.
🎯 REAL QUESTION "For each temperature, how many days until a warmer temperature?" (Daily Temperatures)
  • Stack holds indices of days awaiting a warmer day, in decreasing-temperature order.
  • For each new day i: while stack top has a cooler temp, pop it and record result[top] = i - top.
  • Push i.
  • Anything still on the stack at the end has no warmer day; leave its result at 0.
🔗 BRIDGES Cousin of DFS (DFS IS a stack, usually the call stack). The "monotonic" idea generalizes to monotonic deque for sliding windows. The min-stack pattern is "stack + auxiliary stack" — same idea as prefix sum: remember the running answer alongside the data.
🐍 PYTHON + PRACTICE Stdlib: a plain list is a stack (.append() / .pop() are O(1)); collections.deque for the monotonic-deque variant when you also need O(1) popleft.
Practice: Coding Q15 · Min Stack, Q16 · Balanced Brackets, and Q7 · Next Higher Rated Movie (monotonic stack). Three cards cover stack, monotonic stack, and stack+aux.
📝 PRACTICE PROBLEMS
1. Valid Parentheses / Balanced Brackets
"Is '([{}])' valid?"		Canonical stack. Push openers, pop-and-match on closers, reject if mismatch or stack not empty at end. See Coding Q16.
2. Evaluate Reverse Polish Notation
"Evaluate ['2', '1', '+', '3', '*'] = 9"		Push numbers; on operator, pop two, apply, push result. Stack IS the evaluation state. Watch operand order for non-commutative ops (b op a, not a op b).
3. Min Stack (push/pop/getMin all O(1))
"Stack with O(1) min in addition to push/pop."		Stack + auxiliary stack: main stack holds values; aux stack holds running min. Both push/pop together. See Coding Q15.
4. Next Greater Element (monotonic stack)
"For each element, find the next bigger one to its right."		Monotonic decreasing stack. Iterate right-to-left; pop smaller elements (they can't be anyone's "next greater"); top of stack is the answer. O(n) not O(n²). See Coding Q7.
5. Daily Temperatures
"For each day, how many days until warmer?"		Same monotonic-stack pattern, but stack holds indices (so you can compute the distance when resolving).
6. Largest Rectangle in Histogram
"Given bar heights, find area of largest rectangle."		Hard escalation. Monotonic increasing stack. When popping a bar, the rectangle it defines extends from the current index back to the bar below it. Also used for "Maximal Rectangle" in a 2D grid.


6. BFS + Visited Set   O(V+E)

Signals: "shortest path in unweighted graph", "min hops", "fewest moves", "level order"

💡 WHY IT WORKS BFS explores the graph in increasing order of distance: level 0, then level 1, then level 2. The first time you dequeue the target, you're guaranteed to be on the shortest path in terms of edge count. DFS gives no such guarantee — it might reach the target via a long detour first. The FIFO queue is the crucial invariant.
📝 MENTAL MODEL "Explore by distance. First visit to a node is its shortest-hop distance."
⚠ TRAP Marking visited on pop, not on push. If you mark visited when dequeuing, the same node can get enqueued many times by different predecessors — blowing up time and space. Mark visited at enqueue time. Second trap: using BFS on a weighted graph (edge weights ≠ 1) — that needs Dijkstra. BFS only gives shortest path when edges are unit cost.
🔶 ESCALATION BFS → 0-1 BFS with a deque (edges cost 0 or 1) → Dijkstra (arbitrary non-negative weights, heap replaces queue) → bidirectional BFS (meet in the middle, drastically smaller frontier) → A* (heuristic-guided).
🎯 REAL QUESTION "Given getFriends(person), find the minimum hops between two people (Kevin Bacon number)."
  • queue = [(start, 0)]; visited = {start}.
  • Pop, iterate friends. If friend == target, return distance + 1.
  • Else add unvisited friends to queue and visited.
  • If queue drains, return -1 (unreachable). Mark on enqueue.
🔗 BRIDGES Same machinery as DFS, different data structure (queue vs stack) → different guarantees. Uses a hash set for visited tracking. If you need to reconstruct the path, add a parent dict, then walk backward — same trick as in linked-list traversals.
🐍 PYTHON + PRACTICE Stdlib: collections.deque is the BFS queue (.append() / .popleft() O(1)); use set() for visited tracking; mark visited when enqueuing, not when dequeuing — else you'll revisit.
Practice: Coding Q4 · Connected Cell in a Grid (BFS flood fill), Q17 · Recommendation Distance (shortest path in social graph).
📝 PRACTICE PROBLEMS
1. Shortest Path in a Grid (0s and 1s)
"Min steps from top-left to bottom-right, avoiding 1s."		Canonical unweighted shortest-path. Each cell is a node; 4 neighbors are edges. BFS layer count = minimum steps.
2. Rotting Oranges
"Grid of oranges; rotten ones spread each minute; how many minutes until all rotten?"		Multi-source BFS: enqueue all rotten cells initially, then BFS. The final layer number is the answer. Key unlock for "multiple starts" problems.
3. Word Ladder
"Transform word A to word B one letter at a time, each intermediate must be a valid word."		Graph is implicit: nodes are words, edges are "differ by one letter". Precompute pattern buckets (e.g. h*t, ho*, *ot) for fast neighbor lookup.
4. Binary Tree Level Order Traversal
"Return values grouped by level."		BFS on a tree. Trick: process one level at a time by snapshotting len(queue) before the inner loop — that's the current level's size.
5. Shortest Path in Unweighted Graph (social network)
"Minimum friend-hops between two users."		Same as grid BFS but graph is adjacency list. Parent dict reconstructs the actual path. See Coding Q17 · Recommendation Distance.
6. Number of Islands (BFS flood fill)
"Count connected regions of 1s in a grid."		Iterate cells; when you hit an unvisited 1, BFS to mark the whole island, increment count. DFS works equally — pick whichever feels more natural. See Coding Q4.


7. DFS + Visited Set   O(V+E)

Signals: "all paths", "connected component", "flood fill", "topological sort", "does a path exist"

💡 WHY IT WORKS DFS commits to one branch, exhausts it, then backtracks. This makes it natural for exhaustive exploration (all paths, all configurations), cycle detection, and tree/graph structural problems. Recursion uses the call stack implicitly, which is elegant but caps depth. Each edge is traversed once, giving O(V+E).
📝 MENTAL MODEL "Go deep, backtrack. Use when you need to explore everything, not find the shortest."
⚠ TRAP Using DFS when BFS is required. DFS finds a path; it does NOT find the shortest one. Also: stack overflow on deep graphs (Python recursion limit ~1000) — rewrite iteratively with an explicit stack if depth could exceed that. Flood-fill trap: forgetting diagonal neighbors when the problem says "8-directionally connected."
🔶 ESCALATION Recursive DFS → iterative DFS with explicit stack (avoids stack overflow) → DFS with memoization for DAGs (dynamic programming on graphs) → Tarjan's algorithm for SCCs → backtracking with pruning for constraint satisfaction (N-queens, Sudoku).
🎯 REAL QUESTION "Find the largest connected region of 1s in a 2D grid (8-directional connectivity)."
  • For each unvisited cell containing 1, DFS from it, counting cells reached.
  • Mark visited on entry to avoid re-counting.
  • Neighbors: all 8 offsets (dr, dc) in product([-1,0,1], repeat=2) except (0,0).
  • Track max_region = max(max_region, region_size).
🔗 BRIDGES Sibling of BFS (same traversal machinery, different order). Shares visited set with BFS. Natural fit with recursion and backtracking. For tree problems, DFS is usually easiest because trees have no cycles (no visited set needed) — post-order DFS powers subtree sums, tree DP, and bottom-up pattern matching.
🐍 PYTHON + PRACTICE Stdlib: recursion (watch sys.setrecursionlimit(10_000) for deep grids); or iterative with a list stack. For trees, @functools.lru_cache turns DFS into memoized DP.
Practice: Coding Q5 · Flatten Nested Data Structure (recursive DFS through arbitrary nesting), Q4 · Connected Cells (DFS alternative), Q18 · Serialize Binary Tree (pre/post-order DFS).
📝 PRACTICE PROBLEMS
1. Flatten a Nested List / Dict
"Unwrap arbitrary nesting into a flat structure."		Canonical recursive DFS. Base case: non-container. Recursive case: iterate, recurse into each container. See Coding Q5.
2. Maximum Depth of Binary Tree
"Deepest leaf's depth."		One-liner: 1 + max(depth(left), depth(right)). Base: None → 0. Shows recursive DFS as natural tree-thinking.
3. Number of Islands (DFS flood fill)
"Count connected regions of 1s."		DFS alternative to BFS. Visited is in-place (mutate 1 → 0), or a separate set. Watch recursion limit on big grids — switch to iterative stack. See Coding Q4.
4. All Paths from Source to Target (DAG)
"List every path from node 0 to node N-1."		DFS + backtracking: carry a path list, append current, recurse, pop. Shows the "all of them, not shortest" use of DFS.
5. Serialize / Deserialize Binary Tree
"Encode tree to string; restore from string."		Pre-order DFS with null markers ("1,2,#,#,3,#,#"). Deserialize recursively consuming tokens. See Coding Q18.
6. Detect Cycle in Directed Graph
"Is there a cycle in this DAG?"		DFS with 3-state coloring: WHITE (unvisited), GRAY (in current path), BLACK (done). Hitting a GRAY = cycle. Same idea powers topological sort.


8. Binary Search   O(log n)

Signals: "sorted array, find element", "first/last position", "find the smallest x such that..."

💡 WHY IT WORKS Binary search exploits monotonicity: if a predicate is True on one side of a point and False on the other, you can eliminate half the candidates each check. The real trick is recognizing monotonicity even when it's not explicit — "minimum capacity to ship within D days" is monotonic in capacity even though you're not searching an array.
📝 MENTAL MODEL "Monotonic predicate → halve each step. If I can ask 'is x enough?' in O(?), I can find min/max x in log×that."
⚠ TRAP Off-by-one in bounds. Decide and stick with one template: while left < right with right = mid for lower-bound, OR while left ≤ right with right = mid - 1 for exact match. Mixing mid-values causes infinite loops. Also: integer overflow in (left+right)//2 in Java/C++ — use left + (right-left)//2 (Python doesn't overflow).
🔶 ESCALATION Exact match → lower/upper bound (bisect_left, bisect_right) → binary search on rotated array (check which half is sorted) → binary search the answer (find min/max value satisfying a predicate) → 2D search on matrix with row+column sortedness.
🎯 REAL QUESTION "Find the minimum eating speed k such that you can finish all banana piles within h hours." (binary search on the answer)
  • k is monotonic: if speed X finishes in time, so does X+1.
  • Search space: [1, max(piles)].
  • Predicate: sum(ceil(pile / k) for pile in piles) ≤ h.
  • Lower-bound binary search → first k that satisfies. O(n log max).
🔗 BRIDGES Fundamentally the same intuition as two pointers (both exploit orderings). "Binary search the answer" is a powerful trick: combine with a greedy check function to solve optimization problems that look like DP. Python's bisect module is how you apply it inside a larger algorithm (e.g., LIS via patience sorting).
🐍 PYTHON + PRACTICE Stdlib: bisect.bisect_left(a, x) returns insertion index (first ≥ x); bisect.bisect_right returns first > x; bisect.insort inserts in sorted order. Prefer these over hand-rolled binary search to avoid off-by-one bugs.
Practice: Coding Q3 · Search in Rotated Sorted Array (the canonical "modified binary search" question — decide which half is sorted at each step).
📝 PRACTICE PROBLEMS
1. Classic Binary Search
"Find target in sorted array; return index or -1."		Canonical. Use bisect_left and check if a[idx] == target. Avoids off-by-one errors.
2. Search in Rotated Sorted Array
"Array was sorted, then rotated; find target."		Modified binary search. At each mid, one half is still sorted; check which and whether target lies in that half. See Coding Q3.
3. Find First and Last Position of Element
"For a sorted array with duplicates, find range of target."		Two binary searches: bisect_left for first, bisect_right - 1 for last. Clean use of the _left / _right distinction.
4. Square Root (integer)
"Find floor of sqrt(N)."		Binary search the answer: search for x in [0, N] where x*x ≤ N < (x+1)*(x+1). The "search the answer space, not the input" trick.
5. Koko Eating Bananas (binary search on answer)
"Min eating speed to finish piles in H hours."		Optimization via binary search: search over speeds [1, max(piles)]. At each speed, check if total hours ≤ H (greedy). Huge class of "minimize/maximize X such that feasible(X)" problems.
6. Peak Element
"Find any index i where nums[i] > neighbors (array may not be sorted)."		Surprising use — binary search works on unsorted arrays when an invariant holds. Compare mid to mid+1; go toward the greater side. Guaranteed to find a peak.


9. Heap (Top-K)   O(n log K)

Signals: "top K", "K most frequent", "K closest points", "running median"

💡 WHY IT WORKS A size-K min-heap keeps only the K best candidates seen so far. Each new element is compared against the smallest of the current winners in O(log K); if better, swap. Total work: O(n log K), massively better than sort's O(n log n) when K << n. For streaming problems, this is also constant memory, which sort() can't match.
📝 MENTAL MODEL "Keep only the K winners. Heap of size K, replace the worst with each new arrival."
⚠ TRAP Using the wrong heap direction. For top K largest, use a min-heap (so you can pop the smallest when full). That's counterintuitive. Python's heapq is min-heap only; for max-heap, negate values. For "K closest to origin", store (-distance, point) with a max-heap mental model but a min-heap implementation via negation.
🔶 ESCALATION Size-K heap → heapq.nlargest/nsmallest (library shortcut) → two heaps (running median: max-heap for lower half, min-heap for upper half) → Quickselect O(n) average for static arrays → Count-Min Sketch for approximate top-K on huge streams.
🎯 REAL QUESTION "Return the K most frequent elements in an array."
  • Count with Counter. O(n).
  • heapq.nlargest(k, count.keys(), key=count.get). O(n log k).
  • Or bucket sort by frequency (buckets indexed 0..n) for O(n) if you need to push further.
  • Don't full-sort — that's O(n log n).
🔗 BRIDGES Often paired with Counter (count first, then heap-sort the counts). Dijkstra is a heap-powered BFS. K-way merge uses a heap of iterators. When K = 1, a heap degenerates into "track the max/min" — a single variable.
🐍 PYTHON + PRACTICE Stdlib: heapq.heappush / heappop (min-heap; negate for max); heapq.nlargest(k, it) and nsmallest hide all the plumbing; Counter.most_common(k) internally uses heap. Ties broken by tuple order: (priority, tiebreak, value).
Practice: Coding Q19 · Top 10 Largest Files (heap-of-K on streaming os.walk output). Drill Top K Frequent and K Closest Points mentally.
📝 PRACTICE PROBLEMS
1. Kth Largest Element in an Array
"Find the Kth largest number."		Maintain a min-heap of size K. Iterate; push; if size > K, pop. Top of heap at end is the answer. O(n log K) beats sorting's O(n log n).
2. Top K Frequent Elements
"Most common K elements in an array."		Counter + heap. Build frequency map, then heapq.nlargest(k, counter, key=counter.get). Or counter.most_common(k) — same thing under the hood.
3. K Closest Points to Origin
"Given 2D points, return K closest to (0,0)."		Max-heap of size K (use negative distances). Iterate; push; pop when over size. Top holds the worst of the K best — compare new points against it.
4. Merge K Sorted Lists
"Merge K sorted linked lists into one."		K-way merge via heap. Push first node of each list (with list index). Pop smallest, push its next. Total O(n log K) where n = total nodes.
5. Find Median from Data Stream
"Add numbers; return median at any time."		Two-heap trick: max-heap of smaller half, min-heap of larger half. Median is top of one or average of tops. Rebalance so sizes differ by ≤ 1.
6. Top 10 Largest Files (streaming)
"Stream filenames with sizes; return top 10 by size."		Production use: heapq.nlargest(10, stream, key=lambda x: x[1]) with os.walk feeding the stream. Memory bounded to 10 items, not the whole filesystem. See Coding Q19.


10. Hash Map + Linked List (LRU-style)   O(1) all ops

Signals: "O(1) get + min/max", "LRU cache", "evict oldest", "track order of access"

💡 WHY IT WORKS Hash map gives O(1) lookup but no ordering. Linked list gives O(1) reorder and evict but O(n) lookup. Combining: dict maps keys to nodes in the list. Each operation uses dict for the find and list for the reorder — both O(1). Same pattern underneath min-stack (main stack + auxiliary stack) and pub/sub (dict of event → list of subscribers).
📝 MENTAL MODEL "No single data structure does both; use one for lookup, one for ordering."
⚠ TRAP Forgetting to update recency on get. It's easy to remember on put, but the whole point of LRU is that reading counts as "recently used." Second trap: using a singly linked list — removing a node needs its predecessor, which is O(n) without back-pointers. Always doubly linked. Python shortcut: OrderedDict.move_to_end().
🔶 ESCALATION LRU → LFU (least frequently used) — add frequency buckets → TTL cache (time-based eviction, add expiry timestamps) → distributed cache (Redis with maxmemory-policy allkeys-lru) → segmented LRU (probationary + protected segments, guards hot items from one-hit wonders).
🎯 REAL QUESTION "Design an LRU Cache with capacity c; get and put in O(1)."
  • Doubly linked list with sentinel head and tail.
  • Dict: key → node.
  • On get: find node, unlink, move to front. On put: same, plus evict tail.prev if over capacity.
  • Or OrderedDict with move_to_end() and popitem(last=False).
🔗 BRIDGES Generalizes the "two structures, one for lookup, one for invariant" pattern — same idea as min-stack (stack + aux-stack for min) and prefix-sum (array + hash map for sum-k lookups). Pairs with TTL to build production caches.
🐍 PYTHON + PRACTICE Stdlib: collections.OrderedDict with move_to_end + popitem(last=False) is an LRU in ~10 lines. For decorator-style in-process caches, functools.lru_cache(maxsize=N) gives you one for free.
Practice: Coding Q12 · LRU Cache — drill both the OrderedDict version (for speed) and the hash map + doubly-linked-list version (to prove you understand O(1)).
📝 PRACTICE PROBLEMS
1. LRU Cache (classic)
"O(1) get/put; evict least-recently-used when full."		Canonical. Map from key to node; doubly-linked list ordered by recency. Promote-on-access, evict from tail. See Coding Q12.
2. LFU Cache (Least-Frequently-Used)
"Same contract but evict lowest-use-count; tie-break by recency."		Escalation: one DLL per frequency bucket, plus a map freq → DLL. Promoting moves node across buckets. Harder; LFU is less common in practice.
3. Design a Web Browser History
"Back/forward buttons; new page clears forward history."		Two stacks (back, forward). Each click moves between them. Different use of "map + list" pair but same O(1) mindset.
4. First Unique Number (streaming)
"Return first number seen exactly once so far; updates on each new number."		OrderedDict or (map + linked-list): track count and insertion order. Remove when count > 1. First remaining is the answer. O(1) per operation.
5. Insert/Delete/GetRandom O(1)
"Set supporting insert, delete, and uniform-random element in O(1)."		Map + list (not linked list): map value → list index, list stores values. On delete, swap-with-last-then-pop. Random = list[random.randint(0, len-1)].
6. TTL Cache (time-based eviction)
"Each entry expires N seconds after insertion."		Production variant. Ordered structure keyed by expiry; lazily evict on access. Same "map + ordered secondary structure" template. Redis's EXPIRE does this at scale.


11. Exponential Backoff + Jitter

Signals: "retry", "eventually consistent", "unreliable dependency", "transient failures"

💡 WHY IT WORKS When a dependency has a transient failure, immediate retry hammers it while it recovers (self-inflicted DoS). Exponential backoff delay = base * 2^attempt gives the dependency breathing room. Jitter randomizes the delay so thousands of clients retrying at the "same time" don't converge into a new stampede — known as the thundering herd. Combined with retryable vs non-retryable classification, you don't waste calls on 4xx errors that will never succeed.
📝 MENTAL MODEL "Retry with increasing delay + randomness. Don't retry 4xx. Cap attempts and total time."
⚠ TRAP Retrying non-idempotent operations. Retrying a POST can double-charge a user or create duplicate orders. Fix: idempotency keys (client-generated UUID that the server dedupes). Second trap: unbounded retries — amplifies an outage. Third trap: no jitter — 100k clients retrying at exactly 4 seconds is worse than the original failure.
🔶 ESCALATION Exponential backoff + jitter → decorrelated jitter (AWS's recommended formula for long outages) → circuit breaker (fail fast after N consecutive failures, short-circuit to save the dependency) → bulkhead (separate connection pools so one failing dependency doesn't starve others) → dead-letter queue for messages that never succeed.
🎯 REAL QUESTION "Design a Python decorator that retries an HTTP call on 5xx/timeouts with exponential backoff and jitter, capped at 5 attempts and 60s total."
  • Loop for attempt in range(max_attempts).
  • Try; catch only retryable exceptions (5xx, timeout, connection).
  • Compute delay = min(cap, base * 2**attempt), sleep random.uniform(0, delay).
  • Track total elapsed; break if budget exhausted. Re-raise on final attempt.
🔗 BRIDGES Pairs with circuit breakers (stop retrying when the dependency is clearly down). Retries only make sense for idempotent operations — which ties back to API design. For message systems, retries feed dead-letter queues. Jitter is the same thundering-herd mitigation as in rate limiting.
🐍 PYTHON + PRACTICE Stdlib: time.sleep, random.uniform for jitter. Real code: tenacity library or urllib3.Retry. Key flags: backoff_factor, status_forcelist=[429,500,502,503,504], respect_retry_after_header=True.
Practice: Coding Q11 · Retry with Exponential Backoff — this one is an AFT-critical question. Know how to distinguish retryable (5xx, 429, timeouts) vs not (4xx business errors).
📝 PRACTICE PROBLEMS
1. Retry a Flaky HTTP Call
"Wrap requests.get so it retries up to 5 times on transient failures."		Canonical. Distinguish retryable (5xx, 429, timeouts) from non-retryable (4xx business errors). Exponential delay + jitter. See Coding Q11.
2. Honor Retry-After Header
"Server returns 429 with Retry-After: 30. What do you do?"		Don't use your own backoff; use the server's hint. Parse Retry-After as seconds or HTTP-date; sleep that long; retry. Ignoring this is how you get rate-limit-banned.
3. Idempotency Key for POST Retries
"How do you safely retry a POST /charge request?"		Generate a client-side UUID; send as Idempotency-Key: <uuid>. Server dedupes on this key. Stripe and AWS APIs use exactly this. Retrying an idempotent request = safe; without the key = double-charge.
4. Circuit Breaker
"Stop retrying if a dependency is definitely down."		Escalation of retry. Track failure rate over a window; if > threshold, open the breaker (fail-fast without calling). After cooldown, half-open (one test call). If OK, close. Libraries: pybreaker, Resilience4j. Prevents retry storms on known-dead services.
5. Exponential Backoff + Full Jitter
"Why random(0, 2^n) instead of fixed 2^n seconds?"		Thundering herd prevention. If 1000 clients fail at the same moment and all retry at exactly 2s, they hammer the service again at 2s. With jitter (random 0-2s), they spread over the interval. AWS recommends full jitter: sleep = random.uniform(0, min(cap, base * 2**attempt)).
6. Dead Letter Queue (DLQ) for Exhausted Retries
"After N failed retries on a message, what do you do?"		Send to DLQ for human review; don't keep retrying forever. Standard pattern in SQS, Kafka, RabbitMQ. Monitoring the DLQ depth is how you notice a persistent downstream issue.


12. Token Bucket / Sliding Window Rate Limit

Signals: "throttle", "N per minute per user", "free vs premium tier"

💡 WHY IT WORKS Rate limiting protects you from misbehaving callers and protects your downstream dependencies from you. Token bucket allows bursts (up to bucket size) while capping steady rate — matches how real users behave. Sliding window log is strictly accurate but memory-heavy. Fixed window counter is simplest but has a boundary bug where a burst can double the limit by straddling the window edge.
📝 MENTAL MODEL "Token bucket = burst + steady. Sliding window = accurate + heavy. Fixed window = simple + broken at boundaries."
⚠ TRAP Using wall-clock time (time.time()) for token refill — NTP adjustments, leap seconds, and clock skew cause wrong rates. Use time.monotonic(). Second trap: implementing rate-limit per server when deployed across a fleet — 10 servers × 100 req/min = 1000 req/min actual. For fleet-wide limits, shared Redis with atomic ops (Lua script).
🔶 ESCALATION Per-server in-memory → Redis with INCR + EXPIRE for fixed-window fleet-wide → Redis Lua script for atomic sliding-window check-and-increment → distributed token bucket with Redis hashes → tiered rate limits (free vs premium, different buckets per tier, looked up by API key).
🎯 REAL QUESTION "Design a rate limiter: 100 requests/minute per user, allow bursts of 20."
  • Token bucket: rate = 100/60 tokens/sec, capacity = 20.
  • Per user: {user_id: (tokens, last_refill_time)}.
  • On request: refill tokens based on elapsed time, cap at capacity; if ≥1 token, consume and allow.
  • For fleet-wide: Redis hash with atomic Lua script.
🔗 BRIDGES Shares DNA with sliding window (literally — sliding-window rate limit tracks timestamps). Often paired with circuit breaker for inbound protection. When clients hit the limit, 429 responses feed back into their retry-with-backoff logic — honor the Retry-After header.
🐍 PYTHON + PRACTICE Stdlib: time.monotonic() for jitter-free clocks; collections.deque for the sliding-window variant (timestamps queue); a plain dict {user_id: (tokens, last_refill)} for token bucket. Production: Redis with INCR + EXPIRE.
Practice: Coding Q10 · Rate Limiter — implement both token bucket and sliding window and explain trade-offs (bucket = forgiving burst; sliding = strict).
📝 PRACTICE PROBLEMS
1. Token Bucket Rate Limiter
"Allow up to N requests per second per user; allow bursts up to B."		Canonical. Each user has a bucket; tokens refill at rate N; capacity B. Each request removes a token (rejects if empty). Forgiving of bursts. See Coding Q10.
2. Sliding-Window Rate Limiter
"Exact count: max N requests in any 60-second window per user."		Deque of timestamps. On each request, pop timestamps older than window, check length. Strict — no bursts. Higher memory (one entry per request in window). See Coding Q10.
3. Fixed-Window Counter
"At most N requests per calendar minute."		Simplest but worst: use floor(time / window) as a key; increment a counter in Redis. Downside: edge-burst — a user can send 2N requests across a window boundary. Mention this flaw if asked.
4. Distributed Rate Limit (Redis)
"Same limit across 10 web server instances."		Local limits don't work across instances — user retries until they hit a permissive one. Shared state in Redis: INCR key; EXPIRE key 60; atomic. Trade some latency for correctness.
5. Per-Tier Rate Limits
"Free users: 100/hour. Paid: 10,000/hour. Enterprise: unlimited."		Policy dimension: lookup limit per user based on their tier, then apply standard algorithm. Key the bucket by user_id; the capacity/rate depends on tier. Separates "how to rate-limit" from "what to rate-limit to".
6. Leaky Bucket (outbound shaping)
"Smooth outgoing traffic to exactly N req/sec, queuing excess."		Variant: fixed drain rate, queue absorbs bursts. Good for outbound rate-limiting (don't DDoS downstream). Token bucket is for inbound (protect self).


13. Regex + Counter / awk

Signals: "parse logs", "extract IP/email/phone", "count occurrences in text"

💡 WHY IT WORKS Text-analytics problems all decompose into the same pipeline: extract → normalize → count. Regex handles extraction; a Counter handles aggregation. awk fuses both steps when lines are whitespace-delimited and logic is simple. Streaming line-by-line keeps memory flat regardless of file size — critical for GB-scale logs.
📝 MENTAL MODEL "Extract → normalize to canonical form → count. Stream line by line."
⚠ TRAP Forgetting to normalize before counting. 555-123-4567 and 5551234567 should count as the same number. Strip separators first. Second trap: catastrophic backtracking with nested quantifiers like (a+)+ on pathological input. Third trap: loading a multi-GB file into memory — always iterate for line in f:.
🔶 ESCALATION Python re + Counter → awk for one-liners → structured logging (JSON lines, jq) instead of regex when you control the producer → log aggregators (CloudWatch Logs Insights, Elasticsearch) for fleet-wide search → approximate top-K (Count-Min Sketch) when the distinct-key count itself is huge.
🎯 REAL QUESTION "Given an auth log, report the top 10 IPs by failed SSH login count."
  • Regex: r'Failed password.*from (\d{1,3}(?:\.\d{1,3}){3})'.
  • Stream file line by line; Counter[match.group(1)] += 1.
  • counter.most_common(10).
  • Bash equivalent: grep "Failed password" auth.log | grep -oE '[0-9.]+' | sort | uniq -c | sort -rn | head -10.
🔗 BRIDGES Depends on Counter / hash map for aggregation. Pairs with heap for top-K (counter.most_common(k) uses one internally). For huge logs, upgrade to streaming pipelines (Kafka + workers). The "normalize before count" discipline is the same idea as canonicalization in deduplication.
🐍 PYTHON + PRACTICE Stdlib: re.compile once, reuse; re.findall for all matches, re.finditer for streaming; named groups (?P<ip>\d+\.\d+\.\d+\.\d+) are more readable than indices; collections.Counter for aggregation. CLI equivalents: grep -oE, awk, sort | uniq -c | sort -rn.
Practice: Coding Q20 · Auth Log Parsing, Q21 · sed and awk, Q22 · Regular Expressions, Q6 · IP Validator. This pattern is where AFT interviews live.
📝 PRACTICE PROBLEMS
1. Count SSH Brute-Force Attempts per IP
"Parse /var/log/auth.log, rank IPs by failed login count."		Canonical AFT pattern. Regex for "Failed password … from (IP)". Counter. most_common(). Or one-line shell: grep "Failed password" | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn.
2. Extract All Email Addresses from Text
"Given raw text, list every email address."		re.findall(r'[\w.+-]+@[\w-]+\.[\w.-]+', text). Good enough for most cases; perfect RFC-5322 regex is a famous joke. Know the limits.
3. Validate IP Address (v4)
"Is 192.168.1.300 a valid IPv4?"		Regex alone isn't enough — need range check on each octet (0-255). Split on '.', parse each, validate 0≤n≤255. See Coding Q6.
4. Top K HTTP Endpoints from Access Log
"Parse nginx access log; return 5 most-requested paths."		Full pipeline: regex extract path from log line, Counter, most_common(5). Or shell: awk '{print $7}' access.log | sort | uniq -c | sort -rn | head -5. Both work — Python scales better with parsing complexity.
5. Normalize Phone Numbers Before Counting
"Count unique phone numbers, handling formats: 555-123-4567, (555) 123-4567, 5551234567."		Normalize before counting. Strip non-digits with re.sub(r'\D', '', phone), then feed to Counter. Classic mistake: count raw; you'll miscount equivalent numbers. See Coding Q9.
6. Find Files With "ERROR" and Show Context
"Like grep -B 2 -A 2 ERROR /var/log/*.log but in Python."		Streaming + buffer. Keep a sliding buffer of last N lines; on match, print buffer + next N lines. Shows regex + sliding-window + streaming I/O in one problem.


14. Enums + Abstractions (OOP Design)

Signals: "design a system with several kinds of X", "extensible for future types", "Pizza / Parking Lot / Vending Machine"

💡 WHY IT WORKS Enums replace magic strings with type-safe values — misspelling Size.MEIDUM fails fast at parse time. Abstract base classes / Protocols define contracts so new types can be added without touching existing code (open/closed principle). Favoring composition over inheritance avoids the deep-hierarchy trap (PepperoniLargeStuffedCrustPizza). The whole approach makes change local instead of shotgun surgery across the codebase.
📝 MENTAL MODEL "Fixed set of variants → enum. Fixed contract with varying behavior → interface. Varying attributes → composition."
⚠ TRAP Inheritance for variants that are just different data. class PepperoniPizza(Pizza) is wrong — topping is an attribute, not a type. Second trap: God classes that know everything (Pizza knowing its own price + the catalog + discounts). Separate data from catalog from logic. Third trap: over-engineering — for a 10-line task, skip the interface.
🔶 ESCALATION Enums + simple classes → ABCs / Protocols for polymorphism → Strategy pattern (pluggable algorithm) → Builder pattern (stepwise construction with optional fields) → Dependency Injection (pass collaborators in; don't instantiate them inside) → Domain-Driven Design (aggregates, value objects, repositories).
🎯 REAL QUESTION "Design a Pizza ordering system: sizes, crust types, toppings, tax, promotions."
  • Size, Base: enums. Topping: dataclass (name, price).
  • Pizza: dataclass (size, base, list of toppings). Order: list of pizzas.
  • Catalog (price dicts) lives separately — change prices without touching Pizza.
  • PricingStrategy interface with DefaultPricing, TenPercentOff, WithTax — new rule = new class, no edits to Pizza.
🔗 BRIDGES Connects to nearly every design question: pub/sub (Event Bus) uses abstract Subscriber; config management uses abstract ConfigSource; file filters use composable Predicate. The Strategy pattern appears in pricing, retry policies, rate limits, and caching evictors.
🐍 PYTHON + PRACTICE Stdlib: enum.Enum or enum.IntEnum for fixed variants; dataclasses.dataclass(frozen=True) for value objects (get __eq__, __repr__ for free); typing.Protocol for duck-typed interfaces (no inheritance needed); abc.ABC + @abstractmethod when you want strict base classes.
Practice: Coding Q14 · Pizza Builder — drill this until you can design it cold. It's the OOP question for AFT and covers enums, dataclasses, strategy pattern, and open/closed in one problem.
📝 PRACTICE PROBLEMS
1. Design a Pizza Ordering System
"Sizes, crust types, toppings, tax, promotions; prices change over time."		Canonical. Size and Crust as enums. Topping as dataclass. Pizza as dataclass. Strategy pattern for pricing (Default, TenPercentOff, WithTax). See Coding Q14.
2. Design a Notification System
"Send by Email, SMS, Push, or Slack; users pick preferred channels."		Channel as enum. Sender as Protocol with send(msg); implementations per channel. Compose a user's channels; dispatch over the list. Open/closed: add new channel without editing existing code.
3. Design a Payment Gateway Abstraction
"Support Stripe, PayPal, Square, with same app API."		PaymentProcessor ABC with charge(amount, card). Subclasses per provider. App code depends on the ABC, not concrete classes. Mockable in tests. Swap providers via config.
4. Design an Event Bus / Pub-Sub
"Publishers emit events; many subscribers react; new subscribers without editing publisher."		Observer pattern. Event dataclass. Subscriber ABC with handle(event). EventBus maintains a subscriber list per event type. Demonstrates loose coupling.
5. Design a Shopping Cart with Discounts
"Items, quantities, multiple discount rules (10% off, BOGO, loyalty)."		Strategy pattern for DiscountRule; composable (apply in order or pick best). Cart dataclass. Separating data (items) from logic (discounts) is the point.
6. Design a Ride-Sharing Pricing Engine
"Base fare + distance + time + surge + rider-type discount."		Chain of Responsibility: each PriceComponent adds or multiplies; pass an accumulator object through the chain. Or a list of strategies. Lets you add "promo code" or "airport fee" without breaking existing logic.

🧠 The 30-Second Decision Framework

When an interviewer finishes stating a problem, you have ~30 seconds of thinking silence before it gets weird. Walk this decision tree in your head. Each step should narrow the candidate patterns.

➊ STEP 1 — What's the input shape?
If input is…Reach for…
Sorted arrayTwo pointers, binary search
Unsorted array / listHash map, prefix sum, sort-first-then-pattern
StringSliding window, hash map, stack, two pointers
TreeDFS (recursion), BFS (level-order)
Graph / gridBFS (shortest path), DFS (all paths / components), Union-Find
Stream / unknown lengthHeap (top-K), reservoir sampling, sliding window
IntervalsSort by start, sweep line, heap of end-times
Design / open-endedEnums + interfaces + composition, identify invariants

➋ STEP 2 — What's being asked?
Verb / GoalImplication
Find / searchHash map (exact), binary search (ordered), BFS/DFS (in a graph)
Count / frequencyCounter / hash map; sometimes prefix sum
Shortest / minimumBFS (unweighted), Dijkstra (weighted), sliding window (substring), DP
Longest / maximumSliding window (variable), DP, monotonic stack
Top K / K-thHeap of size K, Quickselect
All (enumerate)DFS / backtracking, BFS for shortest-all
Optimize / maximize valueGreedy (if proven safe), DP (overlapping subproblems), two pointers
Design (build a …)Define data model → identify operations → pick structures per op → scale

➌ STEP 3 — Which constraint unlocks a pattern?
Constraint hintUnlocks
"Sorted" or "monotonic"Two pointers, binary search — O(n log n) / O(log n)
"Unique" / "no duplicates"Hash set lookups; often simpler invariants
"Contiguous" / "subarray"Sliding window, prefix sum — NOT combinations
"In-place" / "O(1) space"Two pointers, cyclic swap, bit manipulation
"All permutations" / "all combinations"Backtracking — exponential is expected
"Huge N, small K"Heap of size K, not full sort — O(n log K)
"Huge file / doesn't fit in memory"Streaming, generators, external sort, chunked reads
"Online / real-time" / "as data arrives"Heap, sliding window, incremental stats
"Values bounded" (0..100, lowercase a–z)Counting sort, fixed-size array as counter — O(n)

➍ STEP 4 — State brute force, then upgrade
Always start by saying the brute force out loud — it shows you understand the problem and gives you a baseline to beat. Then ask yourself the upgrade questions:

  1. "Can a hash map turn O(n2) lookup into O(n)?" — works for two-sum, duplicates, counts, and complement problems.
  2. "Is the data already ordered, or can I order it cheaply?" — unlocks two pointers or binary search.
  3. "Am I recomputing the same subranges?" — prefix sum, sliding window, or memoization fixes it.
  4. "Am I doing a full sort when I only need top K?" — heap of size K.
  5. "Can I process one pass instead of nested passes?" — monotonic stack, single-pass window.
  6. "Do I actually need to materialize everything?" — generator / stream / lazy evaluation.

Interview tip: Narrate this. "Brute force is O(n2) because I'd check every pair. The input is sorted, so I can use two pointers for O(n)." That sentence alone passes many phone screens.


⚡ Rapid-Fire Drill — 10 Questions, <10s Each

Read the problem. Cover the answer column with your hand and call out the pattern out loud in under 10 seconds. If you hesitate, that's a pattern to re-review. Do this 3 times the week before the interview.

# Problem (one line) Your answer →
1 Given a sorted list of numbers, find two that sum to a target. …
2 Find the longest substring that contains at most K distinct characters. …
3 Count how many contiguous subarrays have sum exactly K (negative numbers allowed). …
4 In a stream of integers, return the K largest so far at any time. …
5 Given a maze grid of 0s and 1s, find minimum steps from top-left to bottom-right. …
6 Parse 10GB of access logs and return the 5 most-hit URLs. …
7 Validate a string of brackets like "([{}])". …
8 Build a cache that supports O(1) get and put and evicts the least-recently-used entry. …
9 In a rotated sorted array, check if a target value exists. …
10 HTTP client must tolerate flaky upstream returning 503; keep retrying safely. …

✅ Answers (cover above while reading)

#PatternWhy
1 Two pointers Sorted + pair target → squeeze from both ends; O(n).
2 Sliding window + hash map Variable-size window; map counts chars; shrink when >K distinct.
3 Prefix sum + hash map Count occurrences of prefix - K; negatives kill sliding window.
4 Min-heap of size K Keeps K biggest; pop smaller when full. O(n log K), O(K) memory.
5 BFS + visited set Unweighted shortest path → BFS guarantees min-hops by level.
6 Streaming Counter + heap (or awk | sort | uniq -c | sort | head) Don't load 10GB; stream, count, keep top 5.
7 Stack Push openers, match on closer — LIFO is exactly what nesting needs.
8 Hash map + doubly linked list (or OrderedDict) Map = O(1) find; list = O(1) move & evict tail.
9 Modified binary search Each half is sorted; at mid, decide which half is clean, recurse.
10 Exponential backoff + jitter Distinguish retryable (5xx, 429) from not (4xx); honor Retry-After; cap total time.
