Q1 · Find Top 10 Largest Files/Directories   🟢 HIGH


Problem:   One-liner to find the top 10 largest files or directories under /home/.

SOLUTION · BASH 
# Top 10 with numeric kilobyte sizes
du -sk /home/* | sort -n -r | head -n 10

# Human-readable
du -sh /home/* | sort -hr | head -n 10

# Only files
find /home -type f -exec du -sh {} + | sort -hr | head -n 10

🔍 DEEP DIVE — WHAT EACH PIECE IS DOING

du (disk usage) traverses a directory tree and sums the block sizes of every file. The -s (summary) flag tells it to print only the total for each argument rather than recursing into every subfolder. Without it, you'd get one line per file and the pipe would choke on a large tree. -k forces output in kilobytes (consistent units, parseable by sort -n); -h prints human-readable (KB/MB/GB) — looks nicer but you must pair it with sort -h (human-numeric sort) or the sort will be alphabetical ("10K" < "2M" lexically).

sort -n -r: numeric, reverse. sort -hr is the human-readable variant. Forgetting -n is the classic beginner trap — string sort puts "100" before "99".

du vs df discrepancy (Raises Bar discussion): du walks the filesystem tree and sums file sizes; df asks the kernel how many blocks are actually allocated on the disk. They disagree when a process has a deleted file still open — the directory entry is gone (du can't see it), but the inode is kept alive until the fd closes (df still counts it). Fix: lsof | grep deleted, then restart the holding process. This is a very common AFT-style "disk full but I can't find the files" debugging scenario.

Alternatives worth naming: ncdu (interactive TUI), find /home -size +1G (size-filter at find-time, faster for sparse huge files), du --max-depth=1 (like -s but one level deeper for drill-down), and filesystem quotas (quota, repquota) for prevention rather than detection.

Q2 · sed and awk   🟢 HIGH


Problem:   Explain the difference between sed and awk. Give examples of when you'd use each.

EXAMPLES 
# sed -- stream editor (find/replace, line ops)
sed 's/foo/bar/g' file
sed -n '5,10p' file
sed '/pattern/d' file
sed -i 's/old/new/g' file        # in-place

# awk -- pattern/column processing
awk '{print $1, $3}' file
awk -F: '{print $1}' /etc/passwd
awk '{sum+=$2} END {print sum}' file
awk '/ERROR/ {c++} END {print c}' app.log

🔍 DEEP DIVE — WHEN TO REACH FOR WHICH

sed (stream editor) is built around line-oriented text transformation. It reads one line at a time into a "pattern space", applies your script, and prints the result. Its sweet spot is substitutions and deletions — find/replace across a file or stream. It's faster and terser than awk for pure text munging. The most important flags: -i rewrites in place (accept -i.bak for a safety backup, critical on production boxes); -n suppresses automatic printing (pair with the p command for "print only matching lines", like sed -n '5,10p' to extract a range).

awk is actually a small programming language, not just a tool. It splits each input line into fields (default: whitespace; override with -F, e.g. -F: for /etc/passwd), and lets you run code per line. Use awk when you need columns, arithmetic, state across lines, or conditional logic. The BEGIN { } and END { } blocks run before and after the input — ideal for printing headers or running totals. Associative arrays (counts[$1]++) make awk genuinely powerful for log aggregation: awk '{c[$7]++} END {for (k in c) print c[k], k}' access.log | sort -rn | head gives you top-hit URLs in one line.

Mental rule: "change text → sed. extract or aggregate → awk." For anything more than a simple one-liner, reach for Python — Python beats awk on maintainability once you have state or error handling. perl -pe sits between sed and awk and is worth mentioning if you want to sound like a seasoned Linux engineer.

Common pitfall: using sed with an unescaped / in the pattern (e.g. paths) — use a different delimiter: sed 's|/old/path|/new/path|g'. Another: forgetting that awk's default field separator collapses multiple whitespace (use -F'\t' for strict TSV).

Q3 · Cron Jobs   🟢 HIGH


Problem:   What is cron? How do you schedule a job to run every 15 minutes? How would you troubleshoot a cron job that isn't running?

SOLUTION 
# crontab format: min hour day month weekday command
# Every 15 minutes
*/15 * * * * /path/to/script.sh

# Every day at 02:30
30 2 * * * /usr/local/bin/backup.sh

# Troubleshooting checklist
systemctl status cron            # daemon running?
crontab -l                       # user crontab defined?
grep CRON /var/log/syslog        # cron logs
tail /var/log/cron               # RHEL
# Environment is minimal in cron -- set PATH explicitly
*/15 * * * * PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin /path/script.sh

# Prevent overlapping runs
*/5 * * * * /usr/bin/flock -n /tmp/job.lock /path/job.sh

🔍 DEEP DIVE — WHY CRON JOBS SILENTLY FAIL

The crontab format is five time fields followed by the command: min hour day-of-month month day-of-week command. The classic shorthands are */N (every N units), a comma-separated list (0,15,30,45), a range (9-17), and the special strings @reboot, @daily, @hourly. A subtle trap: day-of-month AND day-of-week are OR'd together, not AND'd — 0 0 13 * 5 runs every Friday and on the 13th, not "Friday the 13th".

Why cron jobs fail in the real world (this is what interviewers probe):
  1. Minimal environment. Cron runs with a nearly empty environment — no .bashrc, no aliases, and $PATH is something like /usr/bin:/bin. Your script's python, aws, or custom binary may work interactively but die in cron. Fix: set PATH= at the top of the crontab, or use absolute paths in your script.
  2. Different working directory. Cron runs from the user's home. Relative paths (./config.yaml) break. Fix: cd to a known directory, or use absolute paths.
  3. Output is lost. stdout and stderr are emailed to the user by default (often not received). Redirect: >> /var/log/myjob.log 2>&1. Set MAILTO="" at the top of crontab to silence delivery attempts.
  4. Overlapping runs. If a 5-minute job takes 7 minutes, two instances run simultaneously, corrupting state. Fix: flock -n /tmp/job.lock cmd — exits immediately if the lock is held.
  5. Daylight savings / missed runs. If the machine was off (laptops), regular cron won't make up missed jobs. anacron is the answer — designed for machines that aren't always on. systemd timers are the modern replacement and offer Persistent=true for the same behavior, plus journald integration.
User vs system cron: crontab -e edits the calling user's cron; /etc/crontab and files in /etc/cron.d/ are system crontabs and include a username column (* * * * * root /bin/foo). For AFT-scale work, systemd timers are increasingly preferred because they log to journalctl and can depend on other units.

Q4 · Auth Log Parsing (Basic CLI)   🟢 HIGH


Problem:   Parse /var/log/auth.log to find login counts, distinct users, and open sessions.

SOLUTION · BASH 
# How many times has joe logged in?
grep "session opened for user joe" /var/log/auth.log | wc -l

# How many distinct users have logged in?
grep "session opened" /var/log/auth.log | awk '{print $NF}' | sort -u | wc -l

# Which sessions are still open?
awk '/session opened/ {u[$NF]++} /session closed/ {u[$NF]--}
     END {for (k in u) if (u[k]>0) print k, u[k], "open sessions"}' /var/log/auth.log

🔍 DEEP DIVE — WHAT /var/log/auth.log IS ACTUALLY LOGGING

On Debian/Ubuntu, /var/log/auth.log is where PAM (Pluggable Authentication Modules) and sshd record every login attempt, session, sudo invocation, and authentication failure. On RHEL/CentOS/Amazon Linux, the same content lives in /var/log/secure. Every successful SSH login produces a line like sshd[12345]: session opened for user joe by (uid=0); a failure produces Failed password for invalid user root from 1.2.3.4 port 22. The session opened / session closed pairing is what lets you compute open sessions — if you just count session opened, you're counting history, not current state.

Why the AWK solution is clean: awk '/pattern/ { code }' runs code only on matching lines. The associative array u[$NF] keys by the last field ($NF is "number of fields" as an index — i.e. the last one), which is the username. Increment on open, decrement on close, then print non-zero at END gives you currently-open sessions in a single pass. This is the idiomatic awk pattern for "stateful log analysis", and interviewers love seeing it instead of multiple grep pipelines.

The subtle traps:
  • Log rotation. auth.log rotates (usually weekly, gzipped to auth.log.1, auth.log.2.gz). To search history: zgrep "pattern" /var/log/auth.log* handles both rotated and gzipped files.
  • Multi-host reality. auth.log on one host only tells you that host's story. Centralized logging (rsyslog → ELK, CloudWatch Logs) is what AFT-scale environments use. Say this out loud.
  • PID matters for precision. Multiple simultaneous SSH sessions for the same user open and close in interleaved order. If you truly care about pairing, track the PID (sshd[12345]) as the key, not the username.
  • Existing tools beat re-inventing: last reads /var/log/wtmp and gives you a pretty login history; lastb reads /var/log/btmp for failed logins; who shows currently-logged-in users (reads /var/run/utmp). Mention these — an interviewer wants to see you know when not to parse text.

RATINGL4 CRITERIA
ConcernCannot use grep/awk/sed; unfamiliar with log file structure.
Mild ConcernAnswers 1 of 3 sub-questions correctly; uses overly complex approaches.
MixedAnswers 2 of 3; commands work but are inefficient.
Meets BarAll 3 using appropriate CLI tools (grep, awk, sort, uniq, wc); correlates opened vs closed for Q3.
Raises BarSingle-pass awk for all three; edge cases (log rotation, PID tracking); alternatives (last/lastlog); monitoring dashboards.


Q5 · SSH Brute-Force Log Analysis   🟢 HIGH


Problem:   Analyze a log file to count failed SSH login attempts per IP address.

Sample entry: Jan 30 11:08:25 prod-db-01 sshd[30067]: Failed password for hacker from 192.168.1.2 port 43367 ssh2

SOLUTION · BASH (one-liner) 
grep "Failed password" /var/log/auth.log \
  | awk '{print $(NF-3)}' \
  | sort | uniq -c | sort -rn

SOLUTION · PYTHON 
import re
from collections import Counter

def count_failed_logins(log_file):
    ip_counter = Counter()
    pattern = r'Failed password.*from (\d+\.\d+\.\d+\.\d+)'
    with open(log_file) as f:
        for line in f:
            m = re.search(pattern, line)
            if m:
                ip_counter[m.group(1)] += 1
    for ip, count in ip_counter.most_common():
        print(f"{ip}: {count} failed attempts")

count_failed_logins('/var/log/auth.log')

🔍 DEEP DIVE — WHY THIS QUESTION GETS ASKED AT AFT

This is a canonical AFT-style question because it exercises the full "parse text → aggregate → act" loop that describes 60% of fulfillment-tech operations work. Understanding why each piece of the pipeline exists beats memorizing the one-liner.

The log line dissected: Jan 30 11:08:25 prod-db-01 sshd[30067]: Failed password for hacker from 192.168.1.2 port 43367 ssh2. Fields separated by whitespace: date(3), host(1), process[pid](1), then the message. The IP address is at position NF-3 (fourth from the end) — which is the trick in the awk one-liner. Position-based parsing is brittle (a slightly different message format breaks it); that's why the Python regex version is more robust and is what you'd actually deploy.

Why the pipeline order matters: grep "Failed password" filters early (fewer lines downstream = faster). awk '{print $(NF-3)}' extracts just the IP (now the pipeline carries small strings, not full lines). sort | uniq -c is the classic "group by and count" in shell — uniq -c only collapses adjacent duplicates, which is why sort must come first. sort -rn at the end orders by count descending. This four-stage pattern (filter → extract → group → rank) is reusable across almost every log analysis question.

When you'd actually use the Python version: when the data is huge (Counter is more memory-efficient than sort-based dedup on 10M lines); when the regex needs to handle IPv6 (grep -oP '(\d+\.\d+\.\d+\.\d+|[0-9a-fA-F:]+)'); when you need to correlate across multiple log files; when the output feeds a downstream alerting system.

The interview escalation: once the count is working, expect "what would you do about it?" — show you understand the response side too:
  • fail2ban watches auth.log live and adds temporary iptables bans for IPs over a threshold.
  • SSH hardening: disable password auth (PasswordAuthentication no in sshd_config), require keys, run SSH on a non-default port (reduces but doesn't eliminate scanning), use AllowUsers / AllowGroups.
  • Defense in depth: security groups / VPC restrictions so SSH isn't exposed to 0.0.0.0/0 in the first place; IAM / SSM Session Manager to avoid SSH entirely.
  • Alerting, not just detection: push the aggregated counts to CloudWatch metrics, alert on >N failures / 5min per source IP.
Saying any two of these out loud moves you from "parser" to "operator".

ConcernCannot extract IP from log line; no understanding of regex/text parsing.
Mild ConcernExtracts IP but cannot count programmatically; hardcodes values.
MixedWorking solution in one language only; doesn't discuss edge cases (malformed lines).
Meets BarExtracts IPs and counts with regex/awk; correct output; sorted by count.
Raises BarBoth Bash and Python; discusses IPv6, malformed entries, log rotation; proposes automation (cron, alerting, fail2ban).


Q6 · Find Most Repeated Phone Number from a File   🟢 HIGH


Problem:   Parse a file containing phone numbers and find the most frequently occurring one.

SOLUTION · PYTHON 
import re
from collections import Counter

def find_most_repeated_phone(file_path):
    phone_pattern = r'\b\d{3}[-.]?\d{3}[-.]?\d{4}\b'
    phone_counter = Counter()
    with open(file_path) as f:
        for line in f:
            for phone in re.findall(phone_pattern, line):
                normalized = re.sub(r'[-.]', '', phone)
                phone_counter[normalized] += 1
    return phone_counter.most_common(1)[0] if phone_counter else (None, 0)

SOLUTION · BASH 
grep -oP '\d{3}[-.]?\d{3}[-.]?\d{4}' phonefile.txt | \
  sed 's/[-.]//g' | sort | uniq -c | sort -rn | head -1

🔍 DEEP DIVE — THE REAL CHALLENGE IS NORMALIZATION

This looks like a "Counter problem" but is secretly a "data cleaning problem". Phone numbers arrive in dozens of formats — 555-123-4567, (555) 123-4567, 555.123.4567, 5551234567, +1 555 123 4567 — all referring to the same physical number. If you count naively, you split one real occurrence across multiple buckets and the "most repeated" answer is wrong. This is the #1 thing interviewers watch for.

The regex dissected: \b\d{3}[-.]?\d{3}[-.]?\d{4}\b
  • \b is a word boundary — prevents matching substrings inside longer numbers (12345678901 would otherwise produce multiple matches).
  • \d{3} means "exactly 3 digits". The {n} quantifier is exact, {n,m} is a range.
  • [-.]? is a character class with an optional match — either hyphen or dot, zero or one time. Inside [ ], most regex metacharacters (including .) lose their special meaning, so this is literally "dash or period".
  • {4} for the last block. Doesn't handle spaces, parentheses, or country codes — a production version needs a richer regex or the phonenumbers library.
Normalization: re.sub(r'[-.]', '', phone) strips separators so "555-123-4567" and "555.123.4567" collapse to the same key. This is the canonicalize before comparing principle — it shows up everywhere: URLs (strip trailing slash, normalize case), email addresses (lowercase, strip dots in Gmail), user-agent strings. Mention the principle in the interview.

Why Counter.most_common(1) is the right tool: it's O(n) to build (each increment is O(1)) and O(n log k) for top-k retrieval (it's backed by a heap internally). Manually iterating with max(dict, key=dict.get) is also O(n) but less idiomatic. The Bash pipeline sort | uniq -c | sort -rn | head -1 is O(n log n) due to the sort; fine for logs up to a few GB.

Edge cases to name out loud:
  • International numbers (+44 20 7946 0958): the phonenumbers library parses these properly and gives you E.164 canonical form.
  • Extensions (555-123-4567 x890): your current regex ignores the extension, which may or may not be correct.
  • False positives (dates like 2024-01-23 could match). The word-boundary helps; stricter: require a character context.
  • PII / compliance: you're mining PII. In a real system, say you'd hash before counting if the output leaves the secure boundary, and check data-retention policy.

MixedWorking but only one phone format; no edge cases.

Q7 · Running Commands Across Thousands of Machines   🟢 HIGH


Problem:   How would you run a command across 1,000 servers simultaneously?

APPROACHES 
# 1) Ansible ad-hoc
ansible all -i inventory -m shell -a "uptime" --forks=50

# 2) parallel-ssh (pssh)
pssh -h hosts.txt -p 50 -t 30 "systemctl status myservice"

# 3) GNU parallel
cat hosts.txt | parallel -j 50 'ssh {} "df -h /"'

# 4) xargs
cat hosts.txt | xargs -I{} -P 50 ssh {} "hostname; uptime"

# 5) AWS Systems Manager (for EC2 fleets)
aws ssm send-command \
  --targets "Key=tag:Environment,Values=prod" \
  --document-name AWS-RunShellScript \
  --parameters 'commands=["uptime"]'

🔍 DEEP DIVE — WHICH TOOL, AND WHY IT MATTERS

At 1,000 hosts, any of these tools works. At 100,000, the choice of tool determines whether your change takes 5 minutes or 5 hours. At AFT-scale (millions of hosts across multiple regions), only purpose-built tooling survives. The interviewer is probing your mental model of each.

xargs & GNU parallel: quickest to reach for; zero extra dependencies. Best for ad-hoc, read-only, short-lived commands (uptime, df -h). Failure collection is crude — you mostly learn "something went wrong on some hosts." Good for exploration, bad for changes.

pssh (parallel-ssh): purpose-built for fan-out SSH. Gives you -t timeouts, output collection per-host (-o outdir), and error files. It's SSH under the hood, so it inherits all SSH's operational baggage (key management, known_hosts, connection limits). Good for "I need output from 1k hosts fast."

Ansible ad-hoc (ansible all -m shell): still SSH underneath, but you get modules (idempotent primitives like yum, copy, systemd — safe to re-run), inventories (static or dynamic from EC2 tags), fact gathering, and structured results. The --forks flag controls parallelism; pair with serial: in a playbook to do batches ("10% first, pause, then 50%, then rest") — this is the key canary deployment pattern.

AWS SSM Run Command: not SSH at all. An SSM agent on each instance polls AWS for work; you submit the command to the API. Benefits: no inbound ports (hosts can be in private subnets with no public IP and no SSH open), IAM-based auth (no SSH keys to manage), CloudTrail audit log, targeting by tag, built-in parallelism controls (--max-concurrency, --max-errors). This is the AWS-native answer and almost certainly what AFT uses internally. If you mention nothing else, mention this.

The scale trap: "just SSH in parallel" breaks around ~500 concurrent connections because of per-user file descriptor limits (ulimit -n), sshd MaxStartups on the target side, and thundering herd if every host tries to pull a 100MB artifact from a single S3 bucket at the same moment. The fixes are:
  • Batching (waves): 1% canary → verify → 10% → verify → 50% → 100%. This limits blast radius.
  • Jitter: sleep a random 0–30s per host before starting the real work — spreads load on shared dependencies.
  • Idempotency: the command must be safe to run twice. Retrying "install package X" should be a no-op if already at X.
  • Audit and output: structured results (JSON), aggregated to a dashboard. At fleet scale, "did it work?" has to be a query, not scrolling output.
Interview escalation: "Now the command is a risky config change" — reach for deploy tooling, not fan-out tooling. That's Terraform/CFN for infrastructure, a deployment pipeline (CodeDeploy, Spinnaker, internal Apollo-style) for applications, and Ansible serial: for stateful edits. Saying "fan-out SSH isn't the right tool for config changes at scale" is a strong senior signal.

Q8 · Executable File Won't Run   🟢 HIGH


Problem:   You copied an executable file from a production server to your local machine, but it won't execute. What could be wrong?

DIAGNOSTIC CHECKLIST 
ls -la ./binary           # permissions (need +x)
chmod +x ./binary

file ./binary             # architecture (x86 vs ARM, ELF vs Mach-O)
ldd ./binary              # missing shared libraries (Linux)
head -n 1 ./binary        # shebang correct? (#!/bin/bash)

mount | grep noexec       # is the fs mounted noexec?
getenforce                # SELinux enforcing?
strace ./binary           # where does it fail?

# Library path issues
LD_LIBRARY_PATH=/custom/lib ./binary
readelf -d ./binary       # dynamic section / needed libraries

🔍 DEEP DIVE — THE LAYERS BETWEEN "./binary" AND ACTUAL EXECUTION

"Why won't this run?" is really "there are six distinct layers the kernel walks through to execute a binary, and any one of them can fail." Naming the layers in order is the interview-winning answer:

1. The executable bit. ls -la shows something like -rw-r--r--. No x, no execution — the kernel's execve() syscall refuses with EACCES. chmod +x adds it. When you copy a file via scp, the permissions are usually preserved; via an email attachment, HTTPS download, or FAT/exFAT USB stick, they are lost. This is the most common cause.

2. The filesystem's noexec flag. mount | grep noexec — many ops environments mount /tmp, /var, and home directories with noexec as a hardening measure. You can have +x and still be blocked. Workaround: move the binary to a permitted location, or use the loader directly (/lib64/ld-linux-x86-64.so.2 ./binary, which sometimes bypasses noexec because the loader is the thing being executed).

3. The architecture. file ./binary tells you "ELF 64-bit LSB executable, x86-64" or "Mach-O 64-bit executable arm64". You copied from production (likely x86-64 Linux) to a local machine that might be an M1/M2 Mac (ARM64, different OS entirely). This is especially common now that Apple Silicon has become standard. The error is typically Exec format error.

4. The interpreter (shebang). For scripts, the first line #!/bin/bash or #!/usr/bin/env python3 tells the kernel which interpreter to invoke. Common failures: Windows line endings (\r\n) break the shebang because the kernel tries to execute /bin/bash\r; hard-coded path #!/usr/local/bin/python that doesn't exist on the target; or the script has no shebang at all, which on many modern systems now fails with Exec format error rather than falling back to /bin/sh. file and head -1 catch these fast.

5. Dynamic linking. ldd ./binary lists every shared library (.so file) the binary needs. If any show => not found, the loader (ld-linux.so) will refuse to run it. Common causes: the binary was built against glibc 2.34 but your system has 2.31 (kernel/libc ABI mismatch); a custom library lives in /opt/myapp/lib but LD_LIBRARY_PATH isn't set. Static binaries (built with -static or Go's default) avoid this entire category; mention them.

6. Mandatory access control. getenforce (SELinux) or aa-status (AppArmor) may block even permitted binaries based on policy labels. audit.log or dmesg shows denials. Common on Amazon Linux and RHEL.

# 7 (User) : 4 + 2 + 1 = rwx
# 5 (Group): 4 + 0 + 1 = r-x
# 5 (Other): 4 + 0 + 1 = r-x

# Remove executable permission (symbolic)

# Alternatives if ls is gone

🔍 DEEP DIVE — PERMISSIONS ARE ACTUALLY ABOUT SYSCALLS

The three permission bits (read, write, execute) map directly to three categories of syscalls the kernel allows. The three classes (user, group, other) determine which set of bits the kernel checks for the calling process.

How the check actually runs: when process with UID U and GIDs G1,G2,… tries to open a file owned by UID F_U and GID F_G with mode M:
  1. If U == 0 (root), the check is skipped for most operations (not all — e.g. executable still requires x on at least one category).
  2. If U == F_U, the kernel checks the user bits only. Your group membership doesn't help you here. Counterintuitive consequence: if a file is mode 077 (---rwxrwx), the owner can't read it, but everyone else can.
  3. If F_G is in the process's group list, check the group bits.
  4. Otherwise, check other bits.
This "first match wins" logic explains weird situations like "I'm in the group but still can't read — the file's owner is me and my user bits say no".

Numeric vs symbolic: 755 is absolute ("set to exactly these bits"); a-x, u+w, g=r are relative ("flip these bits, leave others alone"). Relative mode is safer in scripts that operate on mixed permissions — you don't accidentally make something world-writable. Numeric is faster to type and less error-prone for setting fresh permissions.

Directory permissions are different: r on a directory = "can ls" (read the directory entries). x on a directory = "can cd into it / access a named child". w on a directory = "can create or delete files inside it" (even if you can't write the files themselves — this is how /tmp works; w+t sticky bit lets anyone create but only owner can delete). The common "I can list it but can't read files" or "I can read the file if I know the name but can't list" situations come from mismatched directory vs file permissions.

Special bits (the "4xxx" prefix):
  • SUID (4xxx) on an executable = runs as the file's owner, not the caller. This is how passwd works — owned by root, SUID-set, so any user can edit /etc/shadow indirectly. Huge security footgun; scan your fleet for SUID-root binaries you don't recognize.
  • SGID (2xxx) on a directory = new files inherit the directory's group. Useful for shared project folders.
  • Sticky bit (1xxx) on a directory = only the owner of a file (or root) can delete it, even if others have w on the directory. /tmp has mode 1777.
umask is the "default deny" mask — bits set in umask are removed from default permissions on new files (666 for files, 777 for dirs before mask). umask 022 gives 644 files and 755 dirs; umask 077 gives 600 and 700 (your home files become private even to groupmates).

ACLs when regular perms aren't enough: the 9-bit model can't express "user Alice can read but only user Bob can write". setfacl -m u:alice:r--,u:bob:rw- on a file gives you POSIX ACLs; ls -l shows a + after the permission block (-rw-r--r--+) to indicate the file has ACLs and the basic view is incomplete. Use getfacl to see them.

The "ls is gone" twist catches people off guard. Valid alternatives — echo * uses shell globbing and doesn't need any external command; find . -maxdepth 1 uses the find binary; stat * uses stat; Busybox systems have dir. It's really a test of "do you understand that shell tools are composable?"

🔍 DEEP DIVE — THE INODE MENTAL MODEL

An inode is the file. The filename is not. This is the single most important idea. A filename is just an entry in a directory (which is itself a special kind of file) that maps "notes.txt" → inode #148923. The inode stores everything about the file: permissions, owner UID/GID, all three timestamps (atime, mtime, ctime), size in bytes, link count, and — crucially — the block pointers that tell the kernel where on disk the actual data lives. Filenames and content are decoupled.

Why this matters for hard links vs soft links:
  • A hard link (ln a b) creates a second directory entry pointing to the same inode. Both names are equally "the file"; neither is a "link to" the other. The inode's link count goes from 1 to 2. rm a decrements to 1; b still works. The file's data is freed only when link count hits 0 and no open file descriptors reference it.
  • A soft link (ln -s a b) creates a new, small file whose contents are the string "a". It has its own inode. When you access b, the kernel reads the target path and follows it. If a is deleted, b becomes a dangling symlink and reads fail with ENOENT. Soft links can cross filesystems and point to directories; hard links cannot.
Inode exhaustion — the production incident that baffles juniors: the filesystem runs out of inodes before running out of space. df -h shows 50% used; touch newfile fails with No space left on device. You're staring at half-empty disk; what's going on? Check df -i — the inode table is full. Happens when an app creates millions of small files (mail queues, Puppet caches, crawler downloads, node_modules directories). Fix: delete the small files; or, if the filesystem is ext4 with too few inodes, you're stuck — inode count is fixed at format time. Reformat with mkfs.ext4 -N 10000000 to allocate more, or move to XFS (dynamic inodes).

The "du says 10GB free, df says full" mystery revisited: a process opened /var/log/big.log, then someone rm'd it. The directory entry is gone (du can't find the file), but the inode is still alive because the fd is open — link count is 0 but the reference from the open fd keeps it. Space isn't freed until the process closes or dies. lsof | grep deleted finds these; restarting the holding process (or truncating via > /proc/<pid>/fd/N) releases the space.

Why filesystems matter here:
  • ext4 pre-allocates all inodes at format time (fixed number, typically ~1 per 16KB of disk). Hard to run out unless you have billions of small files. Easy to corrupt diagnosis because "inode count" is a statically allocated resource.
  • XFS allocates inodes dynamically from free space — you won't hit inode exhaustion separately from disk exhaustion. This is why XFS is the default on RHEL / Amazon Linux for large data volumes.
  • btrfs / ZFS don't really have "inodes" as a separate quota; the concept is present but abstracted.
The stat command is how you inspect an inode directly: stat notes.txt shows you inode number, link count, all three timestamps, block count. Two files are the same file iff they have the same inode and the same device (stat -c '%d %i').

🔍 DEEP DIVE — USE-THE-RIGHT-TOOL, GROUPED BY THE QUESTION YOU'RE ANSWERING

An interviewer asking "name the commands" is really asking "have you diagnosed a real issue?" The best answer organizes commands by what question they answer, not by alphabet. Here's the mental mapping:

"Is the box healthy?" uptime (load average, which is itself worth explaining — 1/5/15 minute averages of runnable+uninterruptible tasks; on an 8-core box a load of 8 means fully utilized, 16 means 2x backed up). top / htop for live state; vmstat 1 5 for a snapshot of CPU / memory / IO in 5 one-second intervals; sar if you want historical ("was the box healthy at 3am last Tuesday?") — sar reads data collected by the sysstat service to disk.

"Why is it slow?" Decide which resource first: CPU (top — high %us user, %sy kernel, or %wa iowait?), memory (free -h — check available, not free, because Linux uses free RAM for cache; available accounts for reclaimable cache), disk (iostat -x 1 — %util and await columns tell you if the disk is saturated), network (ss -s for socket summary, sar -n DEV 1 for NIC throughput). High %wa = CPU is idle waiting for disk = your bottleneck is storage.

"What is this process doing?" ps -ef --forest or pstree shows the process tree (useful when a parent dies and a child becomes an orphan); lsof -p PID lists every file, socket, pipe, and device the process has open; ls -l /proc/PID/fd/ is equivalent and doesn't need lsof installed; cat /proc/PID/status shows memory breakdown and thread count; strace -p PID -c attaches and summarizes syscall time (is it stuck in read? futex? poll?). strace has a real performance impact — don't leave it running on hot production processes.

"Can I reach X?" Start at layer 3: ping (ICMP, often blocked by firewalls; absence doesn't mean "can't connect", just "can't ping"). Layer 4: nc -zv host port or ss -tn dst host:port to check TCP reachability. Application layer: curl -v shows the full HTTP request/response including TLS handshake; curl -w '@time.fmt' gives you DNS, connect, TTFB, total times — tells you which phase is slow. mtr is "ping+traceroute live" and reveals intermittent packet loss along the path that static traces miss.

"What's listening, what's connecting?" ss -tnlp (TCP, numeric, listening, processes) replaces netstat -tnlp on modern systems — ss is faster because it reads kernel data via netlink. Connections by state: ss -tn state established. Lots of TIME_WAIT is normal after heavy client-side traffic; lots of CLOSE_WAIT indicates your app isn't closing sockets promptly — a bug.

"DNS is acting up." dig +short example.com for quick resolution, dig +trace to follow the delegation chain from root servers, dig @1.1.1.1 to bypass the local resolver. nslookup is deprecated but still common. Remember: your app might resolve through getaddrinfo, which consults /etc/nsswitch.conf → /etc/hosts first, then DNS — a stale /etc/hosts entry can make "dig says X but my code says Y" behavior.

"I need the raw packets." tcpdump -i any -nn -w /tmp/cap.pcap port 443 captures to a file; pull the file locally and open in Wireshark for real analysis. 🔍 DEEP DIVE — SIGNALS ARE INTERRUPTS, NOT MESSAGES

A signal is a one-bit interrupt delivered by the kernel to a process. Unlike messages, signals carry almost no payload (just the signal number and, optionally, siginfo structure) — they're closer in spirit to hardware interrupts than to IPC. When a signal arrives, the kernel suspends the process at the next safe kernel-to-userspace boundary and invokes either the default action, the installed handler, or nothing (if masked).

The signal lifecycle has three outcomes for any given signal:
  1. Default action (if the process hasn't registered a handler): terminate, core-dump, stop, or ignore — varies by signal.
  2. User-installed handler: process registered one via signal()/sigaction(); the kernel jumps to that function before returning to normal execution. This is how graceful shutdown works.
  3. Masked / blocked: process is currently ignoring it; the signal is queued (for standard signals, at most one pending; for real-time signals SIGRTMIN–SIGRTMAX, a queue).
The critical distinction: SIGTERM vs SIGKILL.
  • SIGTERM (15) is polite. The process sees it, runs any cleanup handler (flush buffers, close connections, write a last log line), and exits. This is what kill PID sends by default. What systemd sends on systemctl stop. What Kubernetes sends before killing a pod. You should always try TERM first.
  • SIGKILL (9) is fatal and uncatchable. The kernel never delivers it to the process — it just dequeues, deallocates, and moves on. That's why SIGKILL can't be trapped, handled, ignored, or survived: the process never runs a single instruction after the signal is delivered. This is why "kill -9 as first resort" is bad practice — you lose all chance of graceful cleanup (open transactions left dangling, temp files left around, child processes orphaned mid-operation).
The less-obvious signals worth knowing:
  • SIGHUP (1): historically sent when a terminal hung up; now by convention used as "reload your config without restarting" (nginx, haproxy, sshd all do this). The name nohup comes from "don't die when the controlling terminal hangs up".
  • SIGINT (2): what Ctrl-C sends. Polite request to stop at a natural boundary.
  • SIGQUIT (3): what Ctrl-\ sends; usually produces a core dump.
  • SIGSTOP (19) / SIGCONT (18): pause and resume a process. SIGSTOP is like SIGKILL in that it can't be caught or blocked — the kernel just freezes the process. Ctrl-Z is the catchable variant (SIGTSTP).
  • SIGUSR1 / SIGUSR2 (10, 12): reserved for application-specific use. nginx uses SIGUSR1 for "reopen log files" after rotation.
  • SIGPIPE (13): sent when you write to a closed pipe — default action is to terminate. This is why "... | head -1" sometimes produces Broken pipe errors from the upstream command after head closes.
  • SIGCHLD (17): sent to a parent when a child exits. Handling it properly (by calling wait()) is how you avoid zombies — see next question.
Signal-safe handlers are restrictive. Inside a handler you can only call async-signal-safe functions (a short list that excludes printf, malloc, most of libc). The usual pattern is to set a flag in the handler and do the real work in the main loop: 
stop = False
def _on_term(signum, frame):
    global stop
    stop = True
signal.signal(signal.SIGTERM, _on_term)
while not stop:
    do_work()
cleanup()
The AFT context: any long-running process you write (oncall automation, queue consumers, batch jobs) should handle SIGTERM gracefully — because that's what systemd, Kubernetes, and AWS ECS will send during rolling restarts. "Does your code trap SIGTERM?" is a real production quality gate. In bash: trap 'cleanup; exit 0' SIGTERM SIGINT at the top of the script.

Process groups and negative PIDs: kill -TERM -- -1234 sends SIGTERM to every process in process group 1234, not just PID 1234. Useful when a shell job has spawned children and you want to terminate the whole tree. The -- prevents -1234 from being interpreted as a flag.

Problem:   What is a zombie process? What is an orphan process? How do you identify and handle them?

        State 'Z' in ps. Cannot be killed -- already dead.
        Fix: kill the parent, or fix the parent to reap children.

Orphan  Parent died first. init (PID 1) adopts and reaps the child.
        Harmless; systemd handles it.

# Identify
ps auxf | awk '$8 ~ /Z/ {print}'    # zombies
ps -o pid,ppid,stat,cmd -a

# Avoid zombies
#   Parent calls wait() / waitpid()
#   OR ignore SIGCHLD (signal(SIGCHLD, SIG_IGN))
#   OR double-fork technique for daemons

🔍 DEEP DIVE — THE LIFECYCLE THAT CREATES ZOMBIES

Every UNIX child process leaves a zombie when it exits. The zombie is not a bug — it's the design. When a child calls exit(), the kernel releases the child's memory and file descriptors but keeps a tiny "termination record" (PID, exit status, resource usage) in the process table. The child is now in state Z ("zombie" / "defunct"), waiting for its parent to collect the exit status via wait() or waitpid(). Once the parent calls wait(), the termination record is freed and the PID is reclaimed. That's reaping.

The problem starts when the parent doesn't reap. Every unreaped child stays in the process table forever. Individually, this is harmless (a zombie uses essentially no resources). In bulk — a web server that forks per request and forgets to wait, a script in a loop that spawns children — you can exhaust the system-wide PID space (default 32768 on Linux; check /proc/sys/kernel/pid_max). When that happens, fork() starts failing with EAGAIN and the whole machine can't spawn new processes. That's a zombie apocalypse in production.

Three ways the parent can reap correctly:
  1. Call wait() explicitly for each child you spawn. In bash: wait $!. In Python: subprocess.run does this automatically; subprocess.Popen requires you to call .wait() or .poll().
  2. Install a SIGCHLD handler that calls waitpid(-1, &status, WNOHANG) in a loop until no children are reapable. This is how event-driven servers do it.
  3. Set signal(SIGCHLD, SIG_IGN) — on Linux, this tells the kernel to auto-reap children and skip generating the SIGCHLD. Simple, but you lose the exit status. Fine for "fire and forget" daemons.
Orphans are the opposite problem and mostly benign. If the parent dies before the child, the child becomes an orphan. The kernel re-parents it to PID 1 (historically init, now systemd on most distros). PID 1 is built to reap children in a tight loop — it's the whole reason the "init" process exists. So orphans are automatically cleaned up when they eventually exit. The child keeps running; it just has a new parent. This is actually the foundation of the classic double-fork daemonization technique: fork once, fork again, have the first fork exit — the grandchild becomes orphaned and adopted by init, detached from the original shell.

The "zombie problem in containers" twist is interview gold. In a Docker container, the process you start is PID 1 inside the container. If your PID 1 is a regular application (Python, Node, your binary) that wasn't written to reap children, and your app spawns child processes (a subprocess.Popen, a forked worker), those children's zombies have nowhere to go. Normal systems reap via systemd; in a container, there is no systemd. Zombies accumulate. Fix: use an init-shim like tini (docker run --init uses it automatically), or set your container entrypoint to dumb-init, or run your app under supervisord. AFT engineers will expect you to know this.

How to actually inspect the state:
  • ps axf (forest view) — shows parent/child relationships.
  • ps -eo pid,ppid,state,comm | awk '$3=="Z"' — lists current zombies.
  • cat /proc/<zombie_pid>/status — the zombie's stats; PPid tells you who should have reaped it. kill the parent if it's the bug.
  • You cannot kill a zombie directly. It's already dead. The entry is freed only when the parent reaps it, or the parent dies (transferring it to init, which reaps).
In practice: a handful of zombies momentarily is normal — they exist in the microseconds between exit and reap. A growing count of zombies over minutes/hours is a parent-process bug. Set an alert on "zombies > N".

Q17 · Systemd & Service Management   🟢 HIGH


Problem:   What is systemd? How do you manage services? How would you create a new systemd service?

# /etc/systemd/system/myapp.service
[Unit]
Description=My Application
After=network.target

[Service]
Type=simple
ExecStart=/usr/local/bin/myapp --config /etc/myapp.yaml
Restart=on-failure
RestartSec=5
User=myapp
WorkingDirectory=/var/lib/myapp
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target

# Apply changes
systemctl daemon-reload
systemctl enable --now myapp.service
systemctl status myapp
journalctl -u myapp -f

🔍 DEEP DIVE — SYSTEMD IS A PROCESS SUPERVISOR WITH OPINIONS

Systemd is what runs as PID 1 on essentially every modern Linux distro. It replaced SysV init (shell scripts in /etc/init.d/ and runlevels 0–6) starting around 2011–2015. Systemd's job is to bring the system up, supervise services (restart them on crash), track their dependencies, collect their logs, and tear them down at shutdown. It does all this with a unified, declarative format: unit files.

Everything is a unit. The unit types you'll actually see:
  • .service — a long-running process (daemon, web server, your app).
  • .socket — a listening socket; enables socket activation (start the service only when a connection arrives).
  • .timer — a scheduled trigger for another unit (cron replacement).
  • .target — a grouping; the equivalent of a SysV runlevel. multi-user.target = traditional runlevel 3 (text-mode multi-user); graphical.target = runlevel 5; default.target is a symlink that points to whichever you boot into.
  • .mount, .device, .path — less common.
The unit file sections:
  • [Unit] — metadata and dependencies. After= = ordering (start this after X); Requires= = hard dep (if X fails, I fail); Wants= = soft dep (try to start X, but I start regardless).
  • [Service] — how to run it. Type=simple (default; systemd considers the service started as soon as ExecStart runs); Type=forking (classic daemon that double-forks; you need PIDFile=); Type=notify (service uses sd_notify() to tell systemd "I'm ready" — cleanest, used by nginx, postfix); Type=oneshot (runs to completion, no persistent process). Restart=on-failure, RestartSec=5 give you automatic recovery with backoff. User=, Group=, WorkingDirectory= for identity; LimitNOFILE=, LimitNPROC=, MemoryMax=, CPUQuota= for resource control (backed by cgroups).
  • [Install] — what happens on systemctl enable. WantedBy=multi-user.target means "when boot reaches multi-user target, pull me in". The enable step creates a symlink in /etc/systemd/system/multi-user.target.wants/.
The daily-use commands:
  • systemctl start/stop/restart NAME — one-time actions.
  • systemctl enable/disable NAME — start on boot or not.
  • systemctl enable --now NAME — enable and start immediately. Common shortcut.
  • systemctl status NAME — last few log lines + current state. First stop when something is wrong.
  • journalctl -u NAME — all logs; -f to follow, --since "1h ago" for time-filtered, -p err for errors only.
  • systemctl daemon-reload — always run after editing a unit file. Systemd caches parsed units; without this, your changes don't take effect.
  • systemctl cat NAME — show the effective unit file (with drop-ins merged).
  • systemctl edit NAME — create a drop-in override in /etc/systemd/system/NAME.service.d/override.conf instead of editing the vendor unit (survives package upgrades).
Systemd timers vs cron — an increasingly popular comparison:
  • Logs go to journald, grep-able with journalctl -u my.timer.
  • Persistent=true catches missed runs for machines that weren't on (anacron replacement).
  • Can depend on other units (run after database is up, not at a fixed time).
  • Accurate OnCalendar= expressions (Mon *-*-* 03:00:00).
  • Runs under full systemd resource controls (CPU/memory limits, user namespaces).
Why journalctl is the log story: systemd collects stdout/stderr of every managed service into a binary journal at /var/log/journal/. Advantages: structured (you can query by time, unit, user, priority); tamper-resistant (FSS seals); automatic rotation. Downside: binary format, so you need journalctl to read it — cat /var/log/... doesn't work. On systems where text logs are still preferred (rsyslog), journald typically forwards there too.

Diagnostic moves for a service that won't start: systemctl status → red failure with exit code. journalctl -xeu my.service → full logs + "hints" about what might be wrong. systemctl list-dependencies my.service → is a required unit down? systemd-analyze verify my.service → syntax check. systemd-analyze blame → which units are slow at boot.

Q18 · Investigating a Misbehaving Process   🟢 HIGH


Problem:   An application admin reports that an application isn't starting properly and points to a running process that appears to be at fault. How do you find out what that process is doing?

SYSTEMATIC INVESTIGATION 
ps auxf                        # identify PID, parent, CPU, mem
top -p PID                     # live resource usage
cat /proc/PID/cmdline          # what was it started with
cat /proc/PID/status           # state, threads, UID, etc.
ls -l /proc/PID/cwd            # working dir
ls -l /proc/PID/fd             # open file descriptors
cat /proc/PID/maps             # memory mappings

strace -p PID -f               # system calls (attach, -f for threads)
ltrace -p PID                  # library calls
lsof -p PID                    # open files, sockets, TCP conns
ss -tnp | grep PID             # network connections
gdb -p PID                     # deep debugging

journalctl -u <unit>           # service logs
dmesg | tail                   # kernel (OOM, segfaults)

🔍 DEEP DIVE — WALKING THE /proc TREE IS THE WHOLE ANSWER

Every answer to this question flows through /proc/PID/. The kernel exposes the full state of every process as a directory of virtual files; most of the standard tools (ps, lsof, top) are really just pretty front-ends for /proc lookups. Knowing the tree directly is what separates "remembers the command" from "can improvise when the tool is missing".

The systematic flow — what to check and in what order:

Step 1: What is this process?
  • cat /proc/PID/cmdline | tr '\0' ' ' — the exact argv it was started with (arguments are null-separated on disk).
  • cat /proc/PID/status — State (R/S/D/T/Z), parent PID (PPid), UID/GID, thread count, detailed memory stats (VmRSS, VmSize, VmData), signals pending/blocked. The first thing to read.
  • ls -l /proc/PID/exe — the actual binary (symlink to the file on disk). Sometimes the running binary is a different version than what's installed right now.
  • ls -l /proc/PID/cwd — current working directory. Often surprising; a daemon started from / vs from someone's home has different behavior for relative paths.
  • cat /proc/PID/environ | tr '\0' '\n' — the environment it was started with. Critical for "works from my shell, not from systemd" debugging (different PATH, missing exports).
Step 2: What state is it in? The state letter in /proc/PID/status is the first triage:
  • R (running) or S (sleeping) — normal. R means on the CPU right now; S means idle waiting for an event (poll, sleep, IO).
  • D (uninterruptible sleep) — stuck in kernel, usually waiting for IO. Can't be killed (not even by SIGKILL) until the kernel op completes. Persistent D-state indicates a hardware / NFS problem.
  • T (stopped) — paused via SIGSTOP/SIGTSTP. Send SIGCONT to resume.
  • Z (zombie) — dead, waiting for the parent to reap (see Q19).
Step 3: What's it using?
  • ls /proc/PID/fd/ — every open file descriptor, as a symlink to its target. Sockets show as socket:[12345], pipes as pipe:[...], regular files as the full path. Counting ls /proc/PID/fd | wc -l shows if the process is leaking fds (compare against cat /proc/PID/limits | grep "Max open files").
  • cat /proc/PID/maps or pmap PID — the complete memory layout. Each line is a mapped region: the heap, stack, each shared library, memory-mapped files. Useful for "why is memory 10GB?" — you can see if it's mostly shared libs (normal), heap (leak suspect), or mmapped files.
  • cat /proc/PID/limits — the resource limits the process is running under. A service suddenly failing to open new connections might be hitting Max open files.
  • cat /proc/PID/io — cumulative bytes read/written, syscall counts. Growing wchar but not write_bytes indicates writes going to cache, not disk yet.
Step 4: What's it DOING right now?
  • strace -p PID -f -c — attach and summarize syscalls for a while, then Ctrl-C to get a count of which syscalls dominated time. "90% of time in futex" → waiting on a lock. "90% in read" → waiting on IO or network. "High open/stat" → lots of filesystem traversal. Be careful: strace slows the process significantly; use briefly, not as a monitor.
  • cat /proc/PID/wchan — the kernel function name the process is currently blocked in. One line, but highly diagnostic: poll_schedule_timeout = waiting on events; sk_wait_data = waiting for network data; do_sys_poll = select/poll loop.
  • cat /proc/PID/stack — kernel stack trace, if CONFIG_STACKTRACE is on. Shows where in the kernel it's blocked.
  • ls /proc/PID/task/ — one directory per thread; each thread has its own /proc/PID/task/TID/ subtree. ps -eLf or top -H -p PID shows threads.
Step 5: What's outside the process?
  • journalctl -u NAME -n 200 — if it's a systemd service, this is where the logs live.
  • dmesg -T | tail -50 — kernel ring buffer. OOM kills, segfaults, NIC issues, disk errors all land here with timestamps (-T formats them human-readable).
  • ss -tnp | grep pid=PID — network connections owned by the process.
  • pidstat -u -r -d -p PID 1 — per-PID CPU, memory, IO per second. Shows trends, not just current state.
Step 6: Going deeper (only when needed).
  • gdb -p PID attaches and gives you a full debugger — backtrace (bt) of every thread (thread apply all bt) tells you exactly where execution is stuck. Detach with detach or quit. Very high impact, very disruptive to the target — use in emergencies.
  • perf record -p PID / perf top -p PID for CPU profiling — shows which functions are hot.
  • core dump via gcore PID — write a snapshot to disk that you can analyze later offline.
The "application admin points to the wrong process" trap: always verify the PID they handed you is actually the problem. ps auxf and walk the process tree; the real problem might be the parent that spawned this process, or a sibling competing for the same resource. This is a common AFT-flavor answer: don't trust the reporter's diagnosis without checking.

# Security
# Don't put secrets in env vars (leaks via /proc/PID/environ)
# Use secrets managers: Vault, AWS SSM Parameter Store, SecretsManager

🔍 DEEP DIVE — THE ENV IS PROCESS-LOCAL AND INHERITED

An environment variable is a key=value string attached to a process, automatically copied to every child the process creates. That inheritance model is the whole point. When you export FOO=bar in a shell, the shell stores it in its own process env; when you run a command (say python), the shell fork()s and the child inherits the entire env; python then inherits it to anything it spawns. The env is visible to the process via /proc/PID/environ (on Linux) and accessed in code via os.environ (Python), getenv() (C).

The export distinction catches people off guard. In bash, FOO=bar sets a shell variable — visible to the current shell but not to child processes. export FOO=bar promotes it to an environment variable, which the shell will include in the env of future children. So: 
FOO=bar          # shell-local
python -c 'import os; print(os.environ.get("FOO"))'   # None

export FOO=bar   # environment
python -c 'import os; print(os.environ.get("FOO"))'   # bar
Why there are so many "profile" files — shell type matters: bash distinguishes between login shells (SSH, console login, bash -l) and non-login interactive shells (opening a terminal inside a GUI, running bash). Each type sources different files:
  • Login shell: /etc/profile → first of ~/.bash_profile, ~/.bash_login, ~/.profile that exists. ~/.bash_profile conventionally sources ~/.bashrc.
  • Non-login interactive shell: /etc/bash.bashrc then ~/.bashrc.
  • Non-interactive (scripts): neither — scripts inherit env from their parent and don't source anything automatically. This is the source of "works in my terminal, fails in cron" problems.
The usual convention: put your interactive tweaks (aliases, prompt) in ~/.bashrc; put the things that should set up your environment (PATH, important exports) in ~/.bash_profile; and have ~/.bash_profile source ~/.bashrc at the end so both shell types see both. That's what most distros ship with.

/etc/environment is special. It's not a shell script — it's read by PAM (the pluggable authentication module system) when a user logs in. Syntax is KEY=value, one per line, no export, no shell substitutions. Because PAM reads it before any shell runs, values set here are visible to login methods that bypass shell profiles entirely — graphical logins, SSH non-shell exec, systemd user services. If you need a variable to be visible everywhere, this is where it goes. /etc/profile.d/*.sh is the system-wide equivalent for shell-specific setup.

Systemd services and env vars: systemd-managed services do not source any shell profile. This trips up a lot of people. You have three options:
  • Environment="FOO=bar" inline in the unit file.
  • EnvironmentFile=/etc/default/myapp — a simple KEY=value file, good for deployable config.
  • ExecStart=/bin/bash -c 'source /etc/myapp.env && exec /usr/bin/myapp' — if you really need shell semantics (substitutions, conditionals).
The security angle (Raises Bar):
  • Any process on the system can read /proc/<your_pid>/environ if it shares your UID (or is root). That means any command you run as yourself can harvest all your env vars. Secrets in env vars are shared with every child process, every library you link, and visible to anyone who can run ps eww PID. This is why the 12-factor-app guidance to "put config in env" needs to be qualified: non-secret config, yes; secrets, prefer a secrets manager and have your app fetch them at startup.
  • The env is copied into every child. If you export AWS_SECRET_ACCESS_KEY and then run npm install, every post-install script has access to your credentials. Be surgical — pass via the command line or use AWS_PROFILE= pointing to a file-backed profile.
  • Command-line arguments are worse than env — visible in ps to everyone. mysql -u root -pHUNTER2 shows HUNTER2 to any process that runs ps. Use the interactive prompt, -p without value, or ~/.my.cnf.
Common "my variable isn't set" debugging flow:
  1. echo $FOO — is it set in my current shell?
  2. env | grep FOO — is it in the exported environment?
  3. cat /proc/$$/environ | tr '\0' '\n' | grep FOO — confirm it's really attached.
  4. If it's set in my shell but not in a subprocess: I forgot export.
  5. If it's not set despite ~/.bashrc: am I in a non-login shell? Is the file even being sourced? Add echo "bashrc ran" at the top and open a new terminal to check.
  6. If it's set interactively but not in cron/systemd: those contexts don't source profiles — set it in the systemd EnvironmentFile or cron line directly.
